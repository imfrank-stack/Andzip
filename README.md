# Andzip

Bandizip 风格的 Windows 压缩工具。**界面是 C#（.NET 10 + Avalonia），压缩/解压内核是 C/C++**
（原样 vendor 的 7-Zip，外面包一层只有 41 个函数的扁平 C ABI）。

两种用法，同一个二进制：免安装的 `dist/Andzip-v<版本>-win-x64.exe`，和双击就装的
`dist/Andzip-Setup-v<版本>-win-x64.exe`（桌面上那个图标带透明通道）。各约 21 MB。

---

## 一、为什么做这个

想解决的是自己每天用的一个工具，顺便把一条工程路线走通：

- **用着顺手**。Bandizip 的交互（首页双栏、树 + 详情列表、右键直接解压、进度条跑完自己消失）
  是很多人已经习惯的形状，照着它做不需要用户重新学。
- **干净**。免安装单文件，或者装到 `%LOCALAPPDATA%` 的正常安装（默认那条路只写 `HKCU`，不要管理员权限；
  2.1.0 起也可以选「为所有用户」，那一条走 `Program Files` + `HKLM`，会弹一次系统确认）；
  改默认程序只动你明确勾选过的格式，
  并且**先把原来的默认值记下来**，取消勾选时还回去；不碰别的软件的 ProgID，
  也不伪造 Windows 的默认应用保护哈希（那条路是绕过系统安全机制，走不得）。
  卸载只收回安装时勾过的那两样 —— 安装器不该顺手删它没做过的事。
- **能力来自真正的引擎，而不是自己造解码器**。7-Zip 的格式覆盖面是事实标准，直接复用它；
  本项目的工作在**接口层与产品层**：把 284 个编译单元的 C++ 收成一个稳定的 C ABI，
  再在上面长出界面、路径安全、重名策略、分卷、进度上报。
- **一条能被别人复用的工程记录**：7-Zip 怎么 vendor、扁平 C ABI 怎么设计、
  跨平台（Windows / Linux x86_64 / Linux aarch64）怎么在同一台 Windows 主机上构建、
  单文件裁剪打包哪些开关真的有效（以及哪些是白费功夫）。踩过的坑连症状带定位过程写在
  [`docs/开发记录.md`](docs/开发记录.md) 里。

**它不打算做的事**：成为 7-Zip 的替代品（功能还差得远）、做全平台原生 UI、
以及任何形式的「绕过系统安全机制来抢占默认程序」。

## 二、现状

| 项 | |
|---|---|
| 主要平台 | **Windows x64** —— 构建、测试、运行、打包都在本机验证过 |
| 格式能力 | 引擎报告 **64 种可读 / 11 种可写**（应用里给 7 种：ZIP、7Z、TAR、TGZ、GZ、BZ2、XZ；7Z 另有 11 种压缩方法可选，见下） |
| 单文件绿色版 | **20.83 MB**（21,839,773 字节，3.0.1 实测）；内核带上五个扩展编码器之后比 2.1.0 重 1.6 MB |
| 正常安装 | 同一个 exe 改名即安装器：**分页向导**（欢迎 → 为哪位用户安装 → 选定安装位置（可改、报所需/可用空间）→ 进度 → 完成），桌面 + 开始菜单快捷方式、开始菜单里还有「卸载 Andzip」，安装目录里另有一个能双击的 `uninstall.bat`。「仅为我自己」那一条全程不要管理员；「为所有用户」落到 Program Files 与 HKLM，装与卸都会弹一次系统确认 |
| 测试 | **1543** 项断言全绿（原生 642 + Core 514 + 界面 213 + P/Invoke 外壳 174），另外每次打包对**产物自己**再跑 25 项安装往返自检 |
| CI | GitHub Actions，Windows 跑与本地完全同一份门禁脚本 `ci.ps1` |
| Linux / macOS | 内核能交叉编译、CI 有真机作业；**界面从未在这些平台运行过** |

功能上它还是一个**前半段做完、后半段在补**的工具：打开、浏览、压缩、解压、文件关联、右键菜单、
查找、密码恢复可用；包内编辑（增删成员）与预览还没开始。请看下面两张清单再决定要不要用。

  正开着的压缩包会按新配色重画一遍。深色不是把浅色取反：主按钮的蓝要**压深**（它是白字的底），
  选中行的蓝要压成深蓝（它是浅字的底），语义色换成粉彩版本，底不用纯黑 ——
  两套调色板与对比度都写在规范 §十。**标题栏现在也跟着变深**（1.7.0 起它是我们自己画的，
  不再依赖那台机器上根本不生效的 DWM 属性）。
  **深色下仍有几处浅色**（勾选框方框、下拉弹出项、提示气泡、滚动条、菜单弹出层），
  原因是 SimpleTheme 没有深色表面色，逐条记在规范 §10.4 与第六节。
- **程序图标**（1.6.0）：蓝底圆角方块 + 两片白纸 + 一条拉链 + 琥珀色拉头。由
  `assets/make_icon.py` 画出来，七档尺寸（16 / 24 / 32 / 48 / 64 / 128 / 256）各自单独构图 ——
  16px 上拉链齿会糊成一团，所以那一档只有三样东西。颜色取自界面同一族令牌，
  小尺寸存无压缩位图（老组件读 PNG 的 16px 会读成空白）。
- **图标配色**（2.5.0，`设置 → 查看 → 图标配色`）：同一张图在应用里**重新画了一遍**，五档渐变、
  四个方向、八套预设、两种字形（溢出裁切 / 镂空负形），改一处立刻重画预览，能导出 SVG 与 512 的 PNG。
  「设为桌面图标」把生成那张落到 `%APPDATA%\Andzip\Andzip.ico`，然后换四处：正在跑的窗口与任务栏、
  桌面与开始菜单的快捷方式（只改图标字段）、已登记的格式图标 `DefaultIcon`，最后通知 shell 重读缓存。
  **只动已经存在的项，`UserChoice` 一个字都不碰**；改了几处就报几处，绿色版没有快捷方式就明说没有。
  「恢复默认」删掉那两张、指回 exe 里那张出厂图。**这张图是算出来的，不是任何生成式素材。**
- **浏览压缩包**：树形目录 + 11 列详情列表（列宽可拖拽、长文字不遮挡）、图标视图带缩略图、
  状态栏汇总；能作为单个归档打开 `archive.7z.001` 这类多卷包。
  子文件夹**默认收着**（根节点展开），要一次全摊开在「设置 → 查看」里勾。
- **在包里找东西**（`查找 → 文件查找`，`Ctrl+F`）：非模态的一张小窗，输入即过滤，
  匹配的是**完整路径**、不分大小写，底下写「找到 3 项（包里共 6 项）」。
  结果列的是完整路径而不是文件名 —— 只显名字，用户就得对着一条 `assets/icons/app.svg`
  想"我搜的那个东西在哪一层"。
  「定位」（或输入框里那下回车）把主列表**跳到它所在的那一层**、选中那一行、滚到位，左边的树跟着走过去，
  窗口不关 —— 查找的天性是"搜一下、看一眼、再改个词"。
  **参考软件那一排的「删除」「解压」两颗按钮这里没有**：往已有包里删成员引擎做不到，
  解压也只认整包，摆上去就是两颗假的。
- **最近的文件**（`文件 → 最近的文件`）：最多 10 条，最新在前，点一下就在当前窗口里打开；
  只有**打开成功**的包才记账（失败的包、被取消的口令不算），文件被删掉后那条记录自己消失。
  列表跨重启保存在 `settings.ini`，底下有「清除最近使用的文件记录」。
- **对压缩包本身的操作**（`文件` 菜单）：**另存为**（原样复制一份，不重压）、
  **删除压缩文件**（`Ctrl+Del`，真的进回收站，删之前先问）、**永久删除压缩文件**（`Shift+Ctrl+Del`，
  确认文案会写清楚它不给反悔的机会）、**打开压缩文件位置**（在资源管理器里选中这个包）。
  这四条只在**正开着压缩包**时可点，首页上是灰的 —— 一条能点、点了什么也不发生的「删除压缩文件」比灰着危险得多。
- **解压**：整包解压与逐条解压两条路径、百分比进度、可取消（**Esc 或右上角的叉号**，进度框上没有按钮）、重名逐个询问（覆盖/跳过/自动重命名）、
  zip-slip 路径防护、非法字符清洗、单顶层目录剥离、ZIP 的 `.z01` 风格分卷拼接、口令保护包先问再解。
  **头加密的 7z**（`-mhe=on`，7-Zip 图形界面的默认）也算：打开时会先要口令，
  同一次运行里输过一遍就不再问（「设置 → 安全 → 本次运行中记住用过的口令」，这一层只在内存里；
  想跨重启保留要另外在同一个页面上打开「保存在 Windows 凭据管理器里」，见下）。
  「选择解压路径」里的目录浏览用的是**系统**的选文件夹对话框（不自己画树），
  并且打开时直接停在当前目标路径。那一格本来就是可编辑下拉，所以 3.0.1 起
  对话框里**没有**「桌面 / 我的文档 / 我的图片 / 我的电脑」那一行快捷按钮了 ——
  四个目标都是上面两条路一步就到的地方，留着一行只是让对话框高一截。
- **压缩**：新建压缩文件对话框（格式、**5 档级别**、口令、分卷、排除 `Thumbs.db`、压缩后测试/删除源文件）、
  ZIP 分卷由 Core 切块实现。级别是 `仅存储 / 极速 / 快速 / 标准 / 极限`，对应引擎 `-mx=` 的
  0 / 1 / 3 / 5 / 9 —— 前三档拼速度，标准档看平衡，极限档只管压得小。级别与方法无关，
  每个编码器自己把这个 0-9 翻译成自己的刻度。
  格式下拉里只有引擎**真写得出来**的那 7 项（ZIP / TAR / TGZ / 7Z / GZ / BZ2 / XZ）；
  参考软件列出的 ZIPX / EXE / LZH / ISO / ZPAQ 是只读项，摆在一个"一定要能做成"的列表里没有意义。
  「文件名」默认跟着选中的东西走：压 `photo.jpg` 得到同目录的 `photo.zip`，
  一次压多个才叫「新建压缩」。
- **压缩方法（2.2.0）**：高级设置面板里选。这张表**按格式给**，且只列引擎真写得出来的：
  ZIP 给 `Deflate（默认）/ 仅存储 / BZip2 / LZMA / LZMA2 / Deflate64 / PPMd`，
  7Z 给 `LZMA2（默认）/ LZMA / PPMd / BZip2 / Deflate / Zstandard / LZ4 / LZ5 / Lizard / Brotli / 仅存储`，
  TAR / GZ / BZ2 / XZ 这类单流或纯打包格式**没有方法可选**（下发 `-mm=` 会被引擎拒绝），
  所以界面上干脆不显示那个下拉，而不是显示一个假的选项。
  选中五种扩展方法之一时，下面会多一行小字说明"这种包别的软件不一定打得开"。
- **拖拽进主窗口**：从资源管理器拖**一个压缩包**进来 → 直接在这个窗口里打开它；
  拖**普通文件 / 文件夹 / 一次拖好几个** → 开「新建压缩文件」对话框并把它们填进输入列表。
  注意这**不是**"加进当前打开的包里" —— 往已有归档追加成员本工具做不到（见下面的未完成清单）。
- **压缩时预分配磁盘空间**（默认关）：开始写入前先按未压缩总量占住簇，好处是一开始就知道这块盘
  放不下，而不是压到 90% 才失败；代价是这期间占的比最终包大很多。
- **压缩时不独占源文件**（默认关）：开着时压缩期间别的程序还能继续写/删这些源文件。
  它**不能**读取别的程序独占的文件 —— Windows 对谁都拒绝（备份语义也一样是共享冲突），
  这样的文件会被跳过，压缩结束时告诉你跳过了哪几个。
- **资源管理器集成**：文件关联（勾选即双击走我们，撤销时还原接管前的默认程序）。
  右键一个**压缩包**只有三项：**用 Andzip 打开**（在窗口里浏览内容，不会顺手解压）、
  **解压**、**解压并删除**。解压的落点看包里装着什么 —— 只有一个文件就直接解出来，
  所有内容都在同一个顶层文件夹里就把那个文件夹整个放出来（不会再套一层同名文件夹），
  零散多个才新建一个以压缩包命名的文件夹收纳，重名依次用「名称 (2)」「名称 (3)」；
  「解压并删除」用同一套落点规则，成功后连分卷一起删。
  右键**其他文件或文件夹**只有两项：**压缩为 ZIP**（直接压）与
  **压缩到…**（打开「新建压缩文件」对话框，可设密码 / 分卷 / 级别，预填好输入与包名）——
  压缩包身上不出现这两项，把 zip 再压成 zip 不是谁想要的功能。
- **完整性检测**：工具栏「测试」与菜单 `文件 → 测试压缩文件`（Ctrl+T）。整个包读一遍校验 CRC
  但不落地，进度窗口报百分比、已读体积与预估剩余时间；结果区分「数据坏了」与「根本没读成」
  （缺文件 / 口令错 / 格式不支持），后者不会被写成"包坏了"。
  2.3.0 起坏掉的成员**一次全列出来**（引擎只报第一个，之后拿同一个句柄接着读剩下的），
  名单封顶 100 个，没查完的老实写成「另有 N 个成员没查完」；
  坏的是 ZIP 时结果框上直接给「尝试修复…」，不用自己去菜单里找。
- **修复损坏的 ZIP**（菜单 `工具 → 修复压缩包`，或测试结果那一屏的「尝试修复…」）：**先量再问** —— 进度条里跑一遍结构扫描，
  骨架对得上就只说一句"没发现需要修复的结构问题"（并讲清这句只管结构、数据要靠「测试」），
  对不上才把三种模式摆出来，且把**扫到的问题**列在模式上方。三种模式：
  **重建中心目录**（数据一个字节不改，最快）、**续接分卷与被截断的包**（`.z01…` 拼成一条流，
  残缺的最后一个成员按实际剩下的写入）、**能修多少修多少**（逐成员真解压，解得出的重打包，
  解不出的列名）。**永远写副本，绝不动原包**；2.3.0 起修完**当场把新包读回来**，结果里那句
  「复查：N 个成员全部校验通过」是引擎读出来的，不是修复器自己的成绩单（测试里另有
  用第三方 `System.IO.Compression` 验收的一份，两边独立）。
- **设置窗口（F5）**：九个页面全部实装 —— 常规、文件关联、上下文菜单、压缩、解压、查看、安全、高级、语言。每一页上的开关都真正接得上线；参考软件上有、这里做不到的项，理由写在第六节。**一个设置键只归一页管**（1.6.0 把「双击压缩包时：打开 Andzip / 直接解压」从常规页搬到解压页，就是这条规则的应用）。2.2.0 把后一档改名成**智能解压** —— 它做的本来就是右键「解压」那一件事（先读清单再决定落点），以前叫「直接解压」是名字在骗人，现在有一条断言把两条路钉到同一个任务上。2.5.0 在**查看**页底下加了「图标配色」整节（见上），页面比对话框高了，于是每一页的根节点换成 `ScrollViewer` —— 这条是**真机截图**发现的，headless 断言"控件在不在"看不出"看不看得见"。
- **帮助菜单（2.8.0）**：三条活的 —— **关于 Andzip（F1）**、**打开 Andzip 安装目录**、**转到官网**
  （`https://github.com/imfrank-stack/Andzip`，地址在代码里只登记一处）。
  关于那一屏四行读数全是**现场取的**：版本取自程序集、压缩内核取自引擎自己的报告
  （所以内核没加载时它不会说好话）、许可证是这包里真的合并了 7-Zip 与几个编码器的事实、
  "所在目录"指的是**这个正在运行的 exe 自己的目录**（绿色版没有安装这一步，
  一台机器上也可能同时装着"给自己"和"给所有用户"两份）。
  「转到用户论坛」仍然灰着 —— 没有那个地址就不摆那一条，拿官网凑一个是最难看出来的假。
  「转到帮助页面」删了：它和「转到官网」是同一个目标换两个名字。
  这一档还立了一条规矩：**菜单里自称"已启用"的每一项，都必须真的接到一条命令**，
  窗口构造时当场核对、对不上就抛 —— 以前这句只写在注释里。
- **密码恢复（工具 → 密码恢复…，2.9.0）**：忘了自己设的口令时，把可能的口令**一个一个真读一遍**。
  两种选法 —— **穷举**（数字 / 小写 / 大写 / 字母+数字 / 自定义字符表，长度 1–12）与**字典**（逐个口令）。
  四条不说假话的规矩：① **开工前先体检**，一个根本不是压缩包、或压根没加密的文件会被当场拒绝并说明原因，
  而不是跑完一亿次之后报"这个范围里没有"；② **判对判错靠把那一格成员整段读完的 CRC** ——
  7z 用错钥解出来是一段合法但错误的字节，只看"能不能打开"会大量误报（头加密的 7z 例外，
  而且这个例外是拿一个故意写错的口令量出来的，不是假定）；③ **速度在这台机器上现场标定**
  （ZIP 约 5000 个/秒、头加密的 7z 约 200 个/秒，差二十多倍），超过 30 分钟先问一句要不要跑；
  大到 `ulong` 装不下、连总数都数不出来的那一种范围**直接不给开始** —— 它既给不出进度也给不出 ETA，
  而这一屏的承诺是开跑之前把"要多久"说实话，**「开始」灰掉的那一行同时写着为什么**；④ **找到、试完、被你停止是三句话**，
  合成一句会让人放弃一个本来能试出来的包。
  恢复出的口令只显示在这一屏上供复制，**不写 `settings.ini`、不写注册表**；
  要不要顺手记进本次运行的口令表是单独的勾选，且默认不勾。
- **密码管理器（选项 → 密码管理器…，3.0.0）**：口令可以**跨重启**保留了 —— 但只存在
  **Windows 凭据管理器**里（LSASS 加密后落盘，默认只有你这个账户读得到），
  **不写 `settings.ini`、不写注册表**这条老规矩一个字没动；开关**默认关**，
  把口令留在机器上是一次要用户点头的交易，不是装完就生效的默认值。
  关掉它会**真的删掉**已保存的全部条目（"以为没了、其实还在"是最糟的一种没生效）。
  那一屏**只有两列：哪个包、什么时候存的**—— 不显示口令、不复制、不做"点一下看明文"，
  也不能在那里添加（添加只有一条路：开着开关，正常打开那个包输一次口令）。
  存进去的一定是**已经把这个包真的解开过**的那一把：解压失败或检测没通过时口令不落盘 ——
  否则下次开机你面对的是"密码错误"，指的是一个你从没输过的口令。
  凭据的目标名是**路径的 SHA-256**，路径本身放在设置文件的索引里 ——
  因为"这台机器上哪些文件是加密的"本身就是一条信息，不该写进一个能被枚举的列表。
  单条凭据有 512 **字节**上限（三个字节一个汉字），超了会**明说"口令没有保存"**而不是静默截断。
  它挡住的是明文落盘和别的账户，**挡不住以你的身份运行的程序** —— 页面上就这么写，不夸口。
- **不建主窗口的快路径**：双击智能解压、右键压缩 / 解压 / 解压并删除 —— 只有一根进度条
  （百分比 + 已处理体积 + 预估剩余时间），跑完自动消失。
- **多语言**：中文 / 英文语言包，481 个键，键集与占位符逐一对齐；界面语言可在设置里换（重启后全面生效）。
- **工程化**：单文件裁剪打包、一次出两件产物、跨平台交叉编译、导出符号核对、CI 门禁、逐版本更新日志。

### 未完成 / 已知限制

- **不能往已有归档追加、删除成员或原地更新**；没有「添加到已有压缩包」「测试并修复」「生成 SFX」。
- **密码恢复只会老实地试**（2.9.0）：穷举与字典两种选法，**单线程**，长度上限 12 位。
  没有掩码（"我确定前两位是 ab"）、没有口令变形（leet / 常见替换）、没有多线程分段并行。
  一个 8 位大小写加数字的口令在这台机器上要跑十几年 —— 这一档不会假装更快，
  它只保证**开跑之前把"要多久"说实话**，并且跑不完的时候说的是"没试完"而不是"没有"。
- **深色模式只覆盖了我们的表面**：勾选框方框内部、滚动条槽仍由 SimpleTheme 画，在深色下偏浅。
  要清掉得给这几类控件各写一份 `ControlTheme`，清单在 `docs/界面设计规范.md` §10.4。
  （标题栏 1.7.0 起是我们自己画的，已经跟着变深；菜单弹出层与下拉列表 1.8.0 起也归我们画了。）
- **列表与树的行悬停没有那颗浮起药丸**：行是 `ListBoxItem` / `TreeViewItem` 模板画的，
  要浮起来得替它们重写 ControlTheme；行悬停仍是 SimpleTheme 的淡色底。
- **在设置窗口里切主题，这个窗口自己不重画**：主窗口立刻重做，设置窗口要关掉重开才换配色。
  1.5.0 就有的粗糙处，记在规范 §10.5。
- **压缩包视图只到「浏览」**：列表右键菜单、列显隐与列宽记忆、双击预览、拖拽解压、图像预览面板都没有。
- **条目「文件说明」（逐条目注释）不支持**，会回报警告而不是静默丢弃。
- **分卷只有 ZIP 真做**：7z / xz 的原生多卷输出未实现。
- **ZIP 的密码只支持 ASCII**（7-Zip 写入端自身的限制），用中文密码请改 7Z。
- **右键菜单是静态注册表动词**，不是 COM shell 扩展：Windows 11 上落在「显示更多选项」二级菜单里、
  一次只处理一个文件或一个文件夹、菜单标题渲染不出实际文件名。
- **默认程序可能被 Windows 挡住**：`FileExts\<ext>\UserChoice` 的优先级高于我们写的注册表值，
  而那个哈希伪造不了（这本来就是为了防第三方抢默认应用）。这类扩展名会在设置里明确列出来，
  并给一个跳到系统设置的按钮。
- 工具栏的「添加 / 删除 / 扫描」仍是禁用占位（「测试」已经接上了）；「帮助 → 转到用户论坛」也是 —— 没有那个地址就不摆那一条。
- **修复只支持 ZIP**：7z 的头是编码过的一整块，残缺后无法可靠重建，所以不碰。1.8.6 起这件事**在点菜单时就说明**，不再弹一个注定失败的模式对话框。
- **五种扩展压缩方法只对 7Z 开放**（2.2.0）：Zstandard / LZ4 / LZ5 / Lizard / Brotli。
  **ZIP 永远不给** —— 那些方法在 ZIP 里用的是非标准方法号，做出来的包 WinRAR、资源管理器、
  原版 7-Zip 都打不开，而用户会把这种包发给别人。这条与内核能力无关，是产品红线，
  两侧各有一条断言钉着（`ZipAdvancedSettingsTests` 与 `Andzip.Native.Tests` 的 `zip refuses …`）。
  引擎现在也能写 `lz4` / `lz5` / `liz` / `br` 这四种单流容器，界面上**没有**跟着放开：
  参考软件不列它们，而这一档要的是"7z 里能选这些方法"。
- **符号链接与 POSIX 权限**没接到界面上。
- **错误框里的异常文本仍是英文**（内核回传的消息直接显示）。
- 完整的逐条清单见 [`docs/开发记录.md` 第六节](docs/开发记录.md)。

## 四、架构一眼版

分层是**单向**的，界面永远看不到 native 的类型：

```
  Andzip.App          Avalonia 界面
        │             只调用 Core 的门面与选项记录
  Andzip.Core         深模块：小的接口 + 大量实现
        │             决定「事情怎么做」：命名、重名、路径安全、分卷、进度
  Andzip.Native       P/Invoke 外壳
        │             41 个 az_* 函数，UTF-8，__cdecl，不透明句柄
  andzip_core.dll     7-Zip 引擎
                      决定「字节怎么变」：识别格式、编解码、CRC、固实块、多卷拼接
```

两个值得单独说的判断：

- **接缝放在 Core 的四个静态门面上**（`ArchiveCreator` / `ArchiveExtractor` / `ArchiveReader` /
  `ArchiveTester`）。换引擎时界面一行都不用改 —— 本项目实际上就这么做过一次。
- **错误模型是翻译而不是透传**。`NativeEngine.Translate` 把引擎错误码映射到 Core 原有的异常类型，
  P/Invoke 的错误码不会成为界面必须知道的契约。

完整推导（为什么接缝这么放、解压为什么有两条落地路径、`PROPVARIANT` 那个间歇性崩溃怎么定位的）
在 [`docs/开发记录.md`](docs/开发记录.md) 第三、七节。

## 五、怎么构建

### 前置

- **Visual Studio 2022/2026 的 C++ 工作负载**（引擎用）。CMake / Ninja 用 VS 自带的即可。
- **.NET 10 SDK**。
- 交叉编译 Linux 时需要 Zig（`native/scripts/provision-toolchain.ps1` 会下载便携版）。
- Windows 上建议用 PowerShell；下面命令在 Git Bash 里请写成 `powershell -ExecutionPolicy Bypass -File …`。

### 1. 先构建压缩内核

```powershell
pwsh native/scripts/build-windows.ps1 -RunTests
```

它会配置并编译 `andzip_core.dll`（约 284 个编译单元，需要几分钟）、跑 537 条原生断言、
核对导出符号恰好是头文件声明的 41 个 `az_*`，最后**把 DLL 暂存到
`src/Andzip.Native/runtimes/win-x64/native/`**。

最后一步是界面工程能找到引擎的前提。**跳过它的话 `dotnet build` 照样成功**，只是程序一起来
就显示「compression engine unavailable」。

### 2. 构建界面与业务层

```powershell
dotnet build Andzip.slnx -c Release
```

### 3. 跑测试

```powershell
dotnet test Andzip.slnx -c Release                      # xUnit：Core + 界面
dotnet run --project src/Andzip.Native.Tests -c Release # 控制台自检，必须单独跑
```

`Andzip.App.UI.Tests` 用 Avalonia 的 headless 平台装配**真实的窗口**去断言控件在不在、可不可用、
点下去设置有没有落盘，另外会把主窗口 / 设置页 / 修复对话框渲染成 PNG 供人眼核对。
它是解决方案的一部分，所以 `dotnet test` 和 CI 门禁会一起跑到。
一个必须知道的边界：**headless 平台不检查线程亲和性**，从工作线程改控件在这里不会抛 ——
所以进度上报这类跨线程的东西，界面测试要断言"回调落在哪个线程"，而不是"有没有炸"。

第二条不能省：`Andzip.Native.Tests` 是不带 xUnit 适配器的控制台程序，`dotnet test` 对它
只会还原、不会运行。

### 4. 运行

```powershell
pwsh run.ps1          # 构建 + 启动主程序
pwsh run.ps1 -Check   # 只构建 + 跑两套测试，不开窗口
```

等价裸命令是 `dotnet run --project src/Andzip.App`。在 Visual Studio 里双击 `Andzip.slnx`
之后直接 F5 也能起主程序。

标题栏应当显示 `Andzip (Professional) · 7-Zip 26.04 (x64) · Release · 60 formats / 7 writable`；
如果显示 `compression engine unavailable`，就是第 1 步没做或没暂存成功。

> 仓库里有好几个 exe，别搞混：**主程序**是 `dist/Andzip-v<版本>-win-x64.exe`（发布版）或
> `src/Andzip.App/bin/Release/net10.0/Andzip.exe`（开发版）。
> `build/native/bin/azgui.exe` 是内核自带的最小验证界面，`azcore.exe` 是命令行工具，
> `Andzip.Native.Tests.exe` 是自检 —— 三个都不是主程序。

### 5. 打包（绿色版 + 安装器两件）

```powershell
pwsh build.ps1                 # 版本 → 测试（不过就拒绝打包）→ 发布 → 内嵌核对 → 两件产物 → 对产物跑 /selftest
```

产物在 `dist/`：

| 文件 | 是什么 |
|---|---|
| `Andzip-v<版本>-win-x64.exe` | 单文件绿色版，下载即用 |
| `Andzip-Setup-v<版本>-win-x64.exe` | 「正常安装」：双击出安装向导 |

**安装器不是第二个程序，是同一个文件改了名** —— 它按自己的文件名判断身份
（`InstallLayout.IsInstallerFile`）。这样两件事同时成立：安装器与应用不可能版本不一致，
而装进电脑里的那份 exe 与绿色版是同一个字节流。安装只做五件事：复制自己到
`%LOCALAPPDATA%\Programs\Andzip`（向导里这一处可以改）、留一个 202 字节的 `uninstall.bat`、
建桌面与开始菜单的 `.lnk`（图标取 exe 内那张带透明的 ICO）、写卸载表、按勾选登记关联与右键菜单。
「仅为我自己」那一条一处都不需要管理员；「为所有用户」把同样的几件事落到
`Program Files` + 公共开始菜单 + `HKLM`，为此把自己以管理员身份重启一次（`runas`），
提权被拒就停在当前那一页说明白，不会悄悄降级成只给自己装 —— **装与卸问的是同一句**（2.4.0 补上了卸那一半）。

**卸载没有单独的 `uninstall.exe`，但有能双击的 `uninstall.bat`**：真卸逻辑在
`Andzip.exe /uninstall` 里（它知道两种作用域、快捷方式、注册表，以及"删掉正在运行的自己"那件事），
一个独立的 exe 要么是那 20.77 MB 的第二份拷贝、要么也只是启动上面那一条的壳 ——
壳用 90 字节的批处理就是同一个东西，还不需要目标机器上有编译器。
它跟着安装目录一起收回；开始菜单里那一项「卸载 Andzip」与控制面板那条 `UninstallString` 走的也是同一条路。

卸自己正在跑的那个 exe 时，Windows 报的是"拒绝访问"而不是"正在使用"，而"退出之后再删"要等的是
**进程真的退出**、不是睡两秒 —— 这两处（2.0.0）都改成了按 `Wait-Process -Id <自己>` 等。
两种作用域各装各的：`InstallLayout.ScopeFor` 按"运行中的这一份 exe 在哪个位置"决定卸载该收哪一处，
所以同一台机器上"只给自己装"和"给所有人装"可以并存，卸的是拉起卸载的那一份。

打包会扫描产物字节确认 `andzip_core.dll` 真的在里面 —— 这个失败原本只在运行时才暴露。

单元测试跑的是**未裁剪的 `Andzip.dll`**，发出去的却是单文件 + 裁剪 + 压缩过的 `Andzip.exe`，
而有些故障只活在这条差别里（1.8.3 那次安装器建不出快捷方式：1101 条断言全绿，产物是坏的）。
所以 `build.ps1` 最后一步**直接执行产物**：`Andzip.exe /selftest` 在临时目录 + 探针注册表键里
真装一次、真卸一次，25 项逐条打 `ok` / `FAIL`，非零退出就拒绝出包。
出包之后还有一步真屏幕核对，脚本是 `tests/gui-probe.ps1` —— 它真的启动
`dist/Andzip-Setup-*.exe`、真的把鼠标点到屏幕坐标上、真的截那块像素
（`PrintWindow` 在 Avalonia 的 GPU 表面上只会是一片黑，所以走 `CopyFromScreen`）。
这两步从 1.8.4 起是固定动作，不再靠"想起来才做一次"。

体积的实测结论（哪些开关有效、为什么不是「换掉链接库形式」能解决的）记在
[`docs/开发记录.md` 第四节第 5 条](docs/开发记录.md)。

## 七、许可证与出处

`native/` 合并了多个上游，机器可读的来源记录在 `native/third_party/MANIFEST.json`。

| 组件 | 许可证 |
|---|---|
| 7-Zip 引擎（`C/`、`CPP/`，原样 vendor，未修改一行） | LGPL-2.1-or-later **附 unRAR 限制** |
| zstd / lz4 / brotli / lizard 等 | BSD-3-Clause / MIT / BSD-2-Clause 等 |
| 上述组件的 7-Zip 封装 | MIT |
| Zig（仅用于交叉编译，不进产物） | MIT |
| SharpZipLib（**只有测试工程引用**，生产代码不依赖） | MIT |

`src/`、`tests/` 以及 `native/src`、`native/include`、`native/tools`、`native/tests`
是本项目的原创工作，沿用 Andzip 自身的许可证。

发布前必须复核两件事：

1. **unRAR 限制**：可以解码 RAR，但不得据此支持 RAR 创建。要宣传 RAR 能力先对照条款。
2. **LGPL 路线**：`andzip_core` 以 DLL 形式动态链接。若改成静态链接发布，需要按 LGPL 提供相应便利。

> 界面与产品设计参考 Bandizip。上游原始压缩包（`cankao/`）与逆向参考语料（`Bandizip-RE/`）
> 都**不在本目录内**：日常构建不需要它们，只有重新 vendor 内核时才需要 `cankao/`。
