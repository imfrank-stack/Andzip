# 压缩基线（阶段 P0）

> `docs/压缩提速-执行流程.md` 第 3 节的交付物。这一张表是后面每一阶段的分母：
> 任何"快了多少"都要拿它比，不拿印象比。
>
> 数据由 `tests/perf/bench.ps1` 产出，原始结果表在
> `docs/perf-results.tsv`（第一次跑）与 `docs/perf-results-repeat.tsv`（第二次跑），
> 两份都入库。本文所有数字都是从这两份表里读出来的，没有一处是估的。

## 0. 怎么复现

```powershell
pwsh native/scripts/build-windows.ps1 -ExtraCodecs      # 产品配置的内核
powershell -ExecutionPolicy Bypass -File tests/perf/bench.ps1
# 冒烟（64 MiB、每格 1 次）：
powershell -ExecutionPolicy Bypass -File tests/perf/bench.ps1 -Quick
```

脚本参数：`-TotalMiB`（默认 512）、`-Repeat`（默认 3）、`-Tsv`（默认 `docs/perf-results.tsv`）、
`-Azcore`、`-WorkDir`（默认 `%TEMP%\andzip-perf-bench`）。跑的是
`build\native\bin\azcore.exe`，不是界面 —— 界面那条路要另算一次开销，见第 6 节"没测什么"。

## 1. 机器与数据

| | |
|---|---|
| CPU | 11th Gen Intel Core i9-11900KF @ 3.50GHz |
| 物理核 / 逻辑核 | 8 / 16 |
| 内存 | 31.9 GB |
| 工作盘 | INTEL SSDPEKKW512G8（NVMe SSD，477 GB，`Provisioning=Fixed`） |
| 引擎 | Andzip 5.4.0 的 `andzip_core.dll`（vendor 7-Zip 26.04，`-ExtraCodecs` 构建） |
| 每组总量 | 512 MiB = 536 870 912 字节（= 16 个逻辑核 × 33 554 432 字节，整除，保证"一个大文件"与"十六个小文件"装的是**同一批字节**） |
| 每格次数 | 3，取中位数；`spread_pct` 是那一格内 3 次的极差/中位数 |

三个语料都是确定性的（`System.Random` 固定 seed，脚本每次把 SHA-256 打在日志里）。
两次跑出来的 digest 完全一致：

| 语料 | 内容 | SHA-256（两次跑都一样） |
|---|---|---|
| `text` | 高冗余文本：重复的英文样例行 + 递增计数 | `1DD4742E…C49C9E` |
| `mixed` | 混合二进制：128 字节定长记录，含单调计数、低熵字段、伪随机尾巴 | `A2CABEFD…62D42E` |
| `rand` | 已压缩/随机数据（压不动的那一类） | `1CD864D7…AE017E` |

**形状对照**是本阶段的核心：`single` = 把这批字节合成**一个**文件压，
`multi` = 拆成 **16 个**（= 逻辑核数）文件压。两边字节内容逐字节相同，
差的只有条目数。

## 3. 一句话结论：洞有多大

**同样的字节，压成一个文件比拆成 16 个文件慢 6.6–9.2 倍**（`mixed`，随级别升高而变宽）：

| 级别 | run1 multi/single | run2 |
|---|---|---|
| zip/Deflate/1 | 6.57× | 6.72× |
| zip/Deflate/3 | 5.93× | 6.79× |
| zip/Deflate/5 | 7.67× | 8.15× |
| zip/Deflate/9 | 9.15× | 8.79× |

三个语料各取 `zip/Deflate/5` 这一格（脚本的 headline，`repeat=3`）：

| 语料 | run1 single | run1 multi | 洞 | run2 洞 |
|---|---|---|---|---|
| `text` | 49.0 | 427.9 | **8.73×** | 8.68× |
| `mixed` | 22.8 | 174.8 | **7.67×** | 8.15× |
| `rand` | 52.1 | 360.5 | **6.92×** | 6.82× |

流程文档给的否决门槛是"洞 < 1.5× 就停"。**实测 6.9–9.2×，门槛过了**，
而且过得很远：洞不只在，还随 CPU 代价升高而变宽（level 1 的 6.6× → level 9 的 9.2×）——
编码器越吃力，"只有一个核在跑"就越贵。

**7z 那条参照线证实了机制**：7z/LZMA2 在 single 与 multi 之间**完全不分开**
（level 1 的 238.6 vs 238.4、level 5 的 36.7 vs 36.5、level 9 的 10.8 vs 11.1，
全在噪声内）。它按**块**并行，一个 512 MiB 的单条目就已经把核摊满了。
所以这不是"我们的机器不行"，是 ZIP 的并行单位决定的。

## 4. 顺带量到的四条（后面几个阶段直接用）

1. **ZIP 的 level 1 与 level 3 是同一个东西。** 两条产物的字节数**完全相同**
   （single 都是 163 888 748，multi 都是 163 892 761），压缩率同为 0.3053，速度 152 vs 153.9。
   → 「压缩级别」这一档在 ZIP 上少一档可用，直接进 P4 的重标定。
2. **ZIP 的最高档是陷阱。** level 9 比 level 3 慢 **117 倍**（1.3 vs 152 MB/s；
   同一批字节的耗时是 381.6 秒 vs 3.37 秒，按秒算是 113 倍），
   换来的是压缩率从 0.3053 到 0.2955，即**小 3.2%**。
   → P4 建议表要正面处理这一格。
3. **7z 连最低档都比 ZIP 最高档又小又快。** 7z/LZMA2/1 = 0.2753 @ 238.6 MB/s，
   zip/Deflate/9 = 0.2955 @ 1.3 MB/s：**小 6.8%，快 184 倍**。
   这是 P1′（大单条目提示换 7z）最硬的一句依据。
4. **7z 的开块多线程会让产物字节数微微漂。** 两次跑里 `7z/LZMA2/5 multi` 是
   142 681 696 vs 142 681 695、`7z/LZMA2/9 multi` 是 141 869 564 vs 141 869 563 ——
   **各差 1 字节**；ZIP 的 8 格与 7z 的 single 格全部逐字节一致。
   含义：MT 分块的边界取决于线程实际抢到多少数据，所以"两次压同一个包得到同一个文件"
   在 7z 多线程路径上不成立（差 1 字节的这个规模不影响判断，但要说清楚）。

另外三条从表里直接能读出来的：`rand` 的压缩率正好 1.0000（512 MiB 随机数据压不动，
单条目只多 148 字节包头，16 条目多 2 198 字节 —— 每条 137 字节左右的 ZIP 头尾开销）；
`text` 高冗余时 Deflate 单条目有 49 MB/s，比 `mixed` 的 22.8 快一倍；
ZIP/Deflate 的 level 5 与 level 1 之间隔了 **6.7 倍**速度（22.8 vs 152）但只差 0.7% 压缩率。

## 5. 两次跑的一致性（否决门槛的第二半）

流程文档要求"两次运行结果差异 < 10%"。**20 格里 17 格达标**，超标的是这三格：

| 格 | run1 | run2 | 偏差 |
|---|---|---|---|
| mixed multi zip/Deflate/3 | 900.8 | 1100.6 | 22.2% |
| mixed multi zip/Deflate/5 | 174.8 | 201.2 | 15.1% |
| mixed single 7z/LZMA2/1 | 238.6 | 266.0 | 11.5% |

三格的共同点是**耗时极短**：0.57 s、2.93 s、2.15 s。
这个量级里线程创建、页缓存调度和磁盘 flush 的固定开销占了主导，
第一格自己的格内极差就有 10.5%（全场最噪）。

要说准话，不能只挑好听的那一侧：
**算洞的那批 ZIP 单条目格（level 1/3/5/9）四次偏差是 5.3 / 6.7 / 8.3 / 7.7%，全在 10% 内**；
超标的 7z/LZMA2/1 single（11.5%）不参与洞的计算，它只是参照线，而且它 multi 那一格
两次跑分别是 238.4 与 260.6 —— 同一条参照线的另一侧也超了 9.3%，
说明"级别最低、速度最快"这一整排的测量分辨率就是不够。
三个语料的 headline 洞两次跑分别为 8.73 / 7.67 / 6.92 与 8.68 / 8.15 / 6.82，
最大相差 **6.3%**（`mixed` 那一档，`text` 只差 0.6%）。

结论按它的实际形状写：**慢的那一侧（真正要等人的一侧）测得稳，快的那一侧测不准，
而快的那一侧不是任何决策的分母**。基线可以用。
要更稳的多条目数字得加大总量或提高 `Repeat`，代价是这一轮已经跑了约 37 分钟。

顺带一条流程上的实话：脚本对 `mixed` 跑了**两遍** `zip/Deflate/5`
（`mixed` 既是主矩阵语料，又在形状对照列表里），表里第 15/16 行就是第二遍。
这不是错误，是重复测量的免费样本：同一次调用之内，single 22.8 vs 25.0 MB/s、
multi 174.8 vs 213 MB/s —— 与上面跨调用的结论一致：**多条目那一侧的噪声就是这么宽**。

## 6. 我**没有**测什么

- **冷缓存**：每格先写盘再读，第 2、3 次基本是热的；第一次才是冷的，没有单独记录。
- **HDD / 混合盘 / 网络盘**：只在这块 NVMe 上测。按条目并行这件事在慢盘上的图像完全不同。
- **大于内存的单文件**：总量 512 MiB ≪ 31.9 GB 内存，页缓存吃下了绝大部分。
  真实场景里 4–16 GB 的单个镜像文件会同时踩到磁盘带宽与固实块/字典的行为差别，这里没覆盖。
- **2 GiB 以上的量级**：流程文档建议 512 MiB–2 GiB，我取下沿，因为 `zip/Deflate/9`
  单条目已经 381.6 秒/次，2 GiB 会让一次跑变成十几小时。
- **解压速度**：一个都没测。压缩快不等于解压快。
- **界面这条路**：全部走 `azcore`，没有经过 Andzip 的进度回调、托管互操作与
  `Dispatcher` 派发；那层开销没算进来。
- **线程亲和性 / 绑核**：没做。`-t` 与 nbWorkers 是 P3 的事（`azcore` 现在有 `-t` 了）。
- **条目数只有 1 和 16 两个点**：中间的 2 / 4 / 8 个条目没扫，
  所以"洞从几倍开始"这条曲线只有一个采样间隔。
- **超过 16 线程**、**同时开多个压缩任务**（真实竞争）：没测。
- **级别的另外几档**：只跑了 1/3/5/9，缺 0/2/4/6/7/8（P4 要的帕累托前沿得补这一排）。
- **其他格式与方法**：gzip、bzip2、xz、tar、以及 7z 上那五个扩展编码器
  （ZSTD / LZ4 / LZ5 / Lizard / Brotli）—— 一个都没测。`-ExtraCodecs` 能写但它们不在表里。
- **内存占用**：`memory_limit_mib` 与 `dict_size_mib` 的交互、以及并行化会不会把内存吃爆，没量。
- **固实关（`--solid=off`）的 7z**：只跑了默认的固实开。

## 7. 参数实验（P3）：`tests/perf/props.ps1`

这一节不改一行内核代码：`az_create_options.extra_properties` 是把任意 7-Zip 属性原样下发到
handler 属性表的通道，`azcore` 现在也补了 `-t`（线程数）与 `-e name=value`（可重复）。
语料是**同一个 `text` 单条目**，只截前 **128 MiB** —— 照第 2 节那个 512 MiB 的格子跑
`zip/Deflate/9` 一次要 380 秒，扫一遍要一整天。
**所以这一节的绝对值不能与第 2 节横比**（128 MiB 的 `text` 单条目 level 3 是 585 MB/s，
512 MiB 的 `mixed` 是 152 MB/s —— 差的是语料与大小，不是设置）；能横比的只有同一批字节内部的相对差。

结果表：`docs/perf-props.tsv`（一行一格；被拒的格子以 `exit_code` 为准，
那一轮的 `mb_per_s` 是假数，见 7-E 最后一条 —— 脚本之后改成失败即写 0，
本轮的表**保持测出来的原样没有回填**）。
表里也没有产物字节数那一列，只有四位小数的比率 —— 而 7-D 那个 `a=0` 的结论要的正是字节数，
所以那几个数是同一批字节上单独定点测出来的（命令列在 7-D 末）。
脚本随后补了 `out_bytes` 列；**本轮表是补之前写的**，下次整轮重跑才会带。

### 7-A ZIP/Deflate 的调优旋钮（128 MiB `text`，level 3）

| 格 | 属性 | MB/s | 压缩率 | 读数 |
|---|---|---|---|---|
| 基准 | — | 585.5 | 0.0019 | |
| fb | `fb=16` | 580.8 | 0.0019 | 与基准同 |
| fb | `fb=64` | 577.3 | 0.0019 | 同 |
| fb | `fb=128` | 583.3 | 0.0019 | 同 |
| fb | `fb=258` | 567.0 | 0.0019 | 同 |
| mc | `mc=16` | 588.5 | 0.0019 | 同 |
| mc | `mc=64` | 582.3 | 0.0019 | 同 |
| pass | `pass=2` | **504.8** | 0.0019 | 慢 14%，**压缩率一点没变** |
| pass | `pass=5` | **460.6** | 0.0019 | 慢 21%，同样没变 |
| a | `a=0` | 573.2 | 0.0019 | ≈基准 |
| a | `a=1` | **49.6** | **0.0020** | **慢 11.8 倍，还更小=更差**（0.0020 > 0.0019） |
| 组合 | `fb=128,mc=64` | 579.8 | 0.0019 | 同 |
| 拒绝 | `mf=bt4` | — | — | 属性收下，**写的时候**被编码器拒（0x80070057） |
| 拒绝 | `algo=1` | — | — | 名字不存在（引擎里叫 `a`），属性阶段就拒 |

三条结论：

1. **`fb` / `mc` 在这台机器这份语料上是"接受了但没用"** —— 六个取值全在 ±3% 的噪声里，
   压缩率一个字节都没动。这一条不能推广成"这两个旋钮没用"：它只说明 level 3 的默认取值
   在这份高冗余数据上已经到了平台期（`mixed` 那种二进制上可能不是，本轮没测，见 7-D）。
2. **`pass` 与 `a=1` 是纯亏。** `pass=5` 花掉 21% 的时间换来零收益；
   `a=1`（另一种解析算法）慢 11.8 倍而产物**更大**（0.0020 对 0.0019）。
   流程文档要找的"更快且不更差"的取值点，在 level 3 这一档**一个都没找到** ——
   找到的三个反向点同样算结果。
3. **`-t` 对 zip/Deflate 完全无效，实测平线**：`mt=1 / 4 / 16` 是 584.4 / 585.1 / 584.9 MB/s
   （0.1% 之差）。这与读码的结论对上了：`DeflateEncoder.cpp:239` 的
   `case NCoderPropID::kNumThreads: break;` —— 它**收下**线程数然后什么都不做。
   这一行是 P1′ 那句建议最直接的机器证据：给 ZIP 加线程不会让那个大文件变快。

### 7-B 7z + Zstandard 的多线程（同一批字节，level 3）

| 线程数 | MB/s | 压缩率 |
|---|---|---|
| 引擎默认（0） | 1349.0 | 0.0005 |
| 1 | **1550.9** | 0.0005 |
| 2 | 1545.1 | 0.0005 |
| 4 | 1514.1 | 0.0005 |
| 8 | 1445.8 | 0.0005 |
| 16 | 1179.2 | 0.0005 |

流程文档里那一问（"上游 `SetZstdThreads` 被注释掉了，显式下发 `nbWorkers` / `mt` 能不能让
7z+ZSTD 吃满多核"）的答案是**否，而且不需要**：

- `nbWorkers` 在这个构建的属性表里**不存在**，两个取值都在属性阶段 `E_INVALIDARG`（表里那两行）；
- `mt` 能下发，但**一个线程就是最快的**（1550.9 MB/s），加到 16 反而掉到 1179（−24%）；
- 压缩率六格全是 0.0005 —— 这份语料本来就不需要多线程去救。

也就是说：ZSTD 这条路在 128 MiB 的量级上**已经快到不是瓶颈**（1.5 GB/s 比内存与磁盘都快），
"吃满多核"在这里不是目标，是负担。上游把 `SetZstdThreads` 注释掉确实是个缺口，
但缺口两边没有水。

### 7-C 参照：7z/LZMA2 level 5 随线程数的曲线（同一批字节）

| 线程数 | MB/s | 相对 1 线程 |
|---|---|---|
| 1 | 54.3 | 1.00× |
| 4 | 267.2 | **4.92×** |
| 16 | 264.6 | 4.87× |

块级多线程**在 4 线程就基本到顶**，16 线程不再涨（128 MiB ÷ 默认分块几何决定了块数）。
这条曲线是 P5（7z 字典 / 块旋钮）要用的形状：**要的是块数与字典，不是线程数上限**。

流程文档问的是"有没有更快且不更差的 `fb` / `mc` / `pass` 取值点"——
`fb` / `mc` 在 level 3 无感，`pass` 只让人变慢；
但**`a`（`NCoderPropID::kAlgorithm`，表里叫 `a` 不叫 `algo`）在 level 9 上是压倒性的**。

为了不把它当成语料巧合，同一件事在三个语料上按**满量 512 MiB 单条目**又测了一遍
（这一组不在 TSV 里，是同一批字节上的定点复核，命令见本节末）：

| 语料 | level 9 默认 | 秒 | `a=0` | 秒 | 快 | 体积 |
|---|---|---|---|---|---|---|
| `text` | 1 056 449 | 27.5 | **1 036 799** | **1.0** | **27.5×** | **小 1.86%（更好）** |
| `mixed` | 158 623 502 | 368.5 | 159 930 836 | 27.9 | **13.2×** | 大 0.82% |
| `rand` | 536 871 060 | 105.3 | 536 871 060 | 84.1 | 1.25× | **逐字节相同** |

三个语料都快，一个更快还更小，一个付出 0.8% 的体积。对照第 4 节那条
（level 9 比 level 3 慢 117 倍只换 3.2%），现在能说得更准：
**界面上那档「极限」的耗时几乎全花在 Deflate 的第二个解析算法上**，
而不是花在"多压了一点"上。

同一条 `fb` 通道在 `mixed` 上就不是免费的（512 MiB，level 9）：
`fb=16` 快 7.9 倍但产物**大 2.32%**（162 303 134 对 158 623 502），
`fb=8` 快 9.8 倍大 1.96% —— 是取舍，不是白拿。所以这一节不能推广成
"把 `fb` 关掉就行"；能推广的是 `a=0` 这一条，而它按流程文档的规矩
**只记录、不写死进产品**，等 P4 用帕累托前沿统一重标定。

复核命令（这三个数不在脚本的矩阵里，是同一批字节的定点测量）：

```powershell

build\native\bin\azcore.exe create out.zip -f zip -m Deflate -x 9          <corpus>-single\all.bin
```

### 7-F 补记：同一条通道，`d` 这个键要的是"带单位的字符串"，不是数字

P5 反推每档默认字典的时候（`docs/perf-p4-p5.md` 第 3.1 节），需要比 1 MiB 更小的字典，
而 `azcore -d` 只吃 MiB。走 `-e` 这条直通通道时撞到两种写法两种结果：

| 写法 | 结果 |
|---|---|
| `-e d=1048576` | `0x80070057 / Win32 87`，`az_writer_finish` 失败，产物 0 字节 |
| `-e d=256k` | 成功，产物与不带 `-d` 的 level 1 逐字节相同 |

原因查到底了，在 `native/third_party/7zip/CPP/7zip/Common/MethodProps.cpp` 里，三层：

1. `IsLogSizeProp`（`:557-571`）把 `kDictionarySize` / `kUsedMemorySize` / `kBlockSize` / `kBlockSize2`
   归为"**对数尺寸**"属性；
2. 这类属性**不走 `ConvertProperty`**，走 `ParseParamsFromPROPVARIANT` 里的一个分支（`:671-677`）；
3. 那个分支 `PROPVARIANT_to_DictSize`（`:257-267`）**两种类型都收，但两种读法不同**：
   `VT_BSTR` 按 `StringToDictSize`（`:218-243`）读"数字 + b/k/m/g 后缀" = 字节数；
   `VT_UI4` 按 `SetLogSizeProp` 读，而这个函数把数当**2 的幂次**（`if (number >= 64) return E_INVALIDARG;`
   然后 `1 << number`）。所以 `d=1048576` 被拒是"**它把这个数当指数了**"（`1 << 1048576` 溢出范围），
   而 `d=20` 才是 1 MiB 的数字写法。

对照 7-A 那次：`fb` 不是对数尺寸属性，走的是 `ConvertProperty`，那张名字表
（`:403-437`，`{ VT_UI4, "fb" }`）说 `VT_UI4` 就得给 `VT_UI4`。
门面的规矩是"全是数字就发 `VT_UI4`，否则发字符串"（`native/src/api/az_writer.cpp:737-751`），
它**只看字符**，不看属性是哪一类 —— 于是同一族的两个键被同一句规矩以**相反**的方向挡住。
`-d` 那个正经选项不受影响，因为它发的是带后缀的字符串：`az_writer.cpp:624-630` 是
`dict_size_mib` 拼上 `m` 再交给 `d`，所以 `-d 32` = 32 MiB ✓（本轮所有字典读数用的都是它）。

读数：这条通道不是"一个名字一个值"，而是要先问"**这个属性是不是对数尺寸**"——
是，就只能给带单位的字符串（或者给幂次）；不是，才照名字表的 VARTYPE 来。
以后要往 `extra_properties` 上加键，先按这两类分，别照 7-A 的经验猜。

复现：

```powershell
$az = 'build\native\bin\azcore.exe'
& $az create x.7z -f 7z -m LZMA2 -x 1 -e d=1048576 <输入>   # Win32 87
& $az create y.7z -f 7z -m LZMA2 -x 1 -e d=256k <输入>      # 成功，与 -x 1 不带 -d 的产物相同
```
