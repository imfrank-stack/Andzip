# 压缩提速：AI Agent 完整执行流程

> 面向「让 Andzip 压得更快」这件事的一份**可交接、可中断、可验收**的执行流程。
> 每个阶段独立成篇：**给 agent 一段提示词 → 它产出可复现的数字或代码 → 达标才进下一阶段**。
>
> 写作依据：`native/README.md`、`docs/开发记录.md`、以及 2026-10-18 对内核源码的实地核对
> （行号见第二节，可能随 vendor 升级漂移，以 `native/third_party/7zip` 当前内容为准）。

---

## 0. 三条总规矩

1. **不许猜性能。** 每一个"快了多少"都必须是一条可复现的命令产出的数字。引用别人的 benchmark、引用我（人）说过的话、引用 README 里的旧数字——都不算证据。
2. **不许改 `native/third_party/` 一行。** 那里是原样 vendor 的上游。要加编码器，走"新增一个命名空间 + 注册进 registry"的路（`ZstdForkEncoder` 是现成的范本），不是改上游。
3. **每阶段有否决门槛。** 达不到就停，写清楚为什么停，然后问人。**不许靠"我再调一下参数"续命**——这个项目已经用 `/selftest` 和 `gui-probe` 证明了"测的是 A、跑的是 B"是真实存在的失败模式。

## 2. 已经查清的事实（直接告诉 agent，省掉它重新摸一遍）

| 事实 | 位置 / 依据 |
|---|---|
| `num_threads` / `multi_thread` **已经下发**成引擎的 `mt` 属性 | `native/src/api/az_writer.cpp:646-648` |
| **ZIP 的并行单位是「条目」不是「块」**：线程数被待压缩文件数截断 | `.../7zip/Archive/Zip/ZipUpdate.cpp:1025-1026` `numZipThreads_limit = numFilesToCompress`；线程体在同文件约 1247 行 `CThreads threads` |
| **没有 Mt 版 Deflate 编码器**（LZMA2 那边有块级 MT，Deflate 没有） | `CPP/7zip/Compress/` 只有 `DeflateEncoder.cpp` |
| Deflate 编码器**经 codec registry 取得**，不是硬编码 new | `ZipAddCommon.cpp` → `CPP/7zip/Common/CreateCoder.h` 的 `CreateCoder_Id` |
| **7z + ZSTD 的线程自动分配逻辑在上游被注释掉了** | `ZipUpdate.cpp` 里 `SetZstdThreads` 整段在 `/* ... */` 内 |
| `extra_properties` 是换行分隔的 `name=value` 直通通道 | `native/include/andzip/andzip.h`，可直接下发任意 7-Zip 属性 |
| 级别映射 EngineLevel = 0 / 1 / 3 / 5 / 9 | `src/Andzip.Core/Archive/CompressionLevelOption.cs` |
| **红线：ZIP 只用标准方法**（非标准方法号的 zip 别人打不开，内核 `E_NOTIMPL` 拒） | `native/README.md` 已知限制；`CompressionMethodOption.cs` 注释 |

**一句话结论**：Andzip 现在压一个目录里几百个小文件已经吃满多核；**压单个大文件的 ZIP，只有 1 核在跑**。这就是要补的洞。

## 3. 阶段 P0 — 基线（不可跳过）

### 目标
量出「按条目并行」这个洞的**精确尺寸**，以及 Deflate 各档级别的真实 MB/s。后面所有阶段都拿它当分母。

### 提示词

```
【阶段 P0：基线测量】

做两件事，只做两件事。

一、写一个可重复运行的基准脚本 tests/perf/bench.ps1（PowerShell，Windows）。
它必须：
1. 生成确定性的测试数据（不要用随机字节糊弄，用三类：高冗余文本、混合二进制、已压缩/随机数据），
   总量建议 512 MiB ~ 2 GiB，用固定 seed 或固定生成算法，保证两次跑出来字节一致。
2. 对每一组配置跑 N 次（N>=3）取中位数，记录：wall time、输入字节、产物字节、MB/s、压缩率。
3. 必须包含这两组对照，它们是本阶段的核心：
   (A) 同样的字节量，作为【1 个大文件】压成 zip/Deflate
   (B) 同样的字节量，拆成【N 个文件】压成 zip/Deflate（N = 逻辑核数）
   (A) 与 (B) 的 MB/s 之比，就是"按条目并行"这个洞的尺寸。
4. 矩阵至少覆盖：zip/Deflate × level {1,3,5,9} × {单文件, 多文件}；
   外加 7z/LZMA2 × level {1,5,9} 作为参照（7z 是块级 MT，本应随核数扩展）。
5. 用 build\native\bin\azcore.exe 跑，不要用界面。

二、把结果写进 docs/perf-baseline.md，包含：
   - 完整的矩阵表（配置 / MB/s / 压缩率 / 耗时）
   - 机器信息（CPU 型号、物理核/逻辑核、内存、磁盘类型 SSD 还是 HDD）
   - 一句话结论：(A) 比 (B) 慢多少倍？7z 那条参照线随核数扩展了吗？
   - 明确写出"哪些数字我没测"

不要改任何产品代码。本阶段唯一的产出就是脚本和那张表。
```

### 验收判据
- `tests/perf/bench.ps1` 能一条命令跑完，两次运行结果差异 < 10%。
- `docs/perf-baseline.md` 里有完整矩阵 + 机器信息。
- **(A) 与 (B) 的比值是一个具体数字**，不是"明显更慢"。

### 交付物
`tests/perf/bench.ps1`、`docs/perf-baseline.md`

### 否决门槛
若 **(A)/(B) 差距 < 1.5×**，说明洞不在"按条目并行"（可能是 I/O 或别的瓶颈占了主导）。
**停止 P1，回来重新 profile**，不要硬做块级并行。

## 5. 阶段 P1 — 大条目块级并行 Deflate（最高 ROI）

### 目标
单条目超过阈值时，切成 N 块并发压缩，拼成**一条合法的 deflate 流**。格式不变、兼容性不变。

### 5.1 P1-a：可行性判读（先读，不要先写）

```
【阶段 P1-a：可行性判读，只许读代码，不许改代码】

读 native/third_party/7zip/CPP/7zip/Compress/DeflateEncoder.cpp 与 DeflateEncoder.h，
回答四个问题，每条都给出文件行号作为依据：

1. NCompress::NDeflate::CEncoder 是 one-shot 还是 streaming？
   它的 Code() 能否分多次喂入、能否中途 flush？
2. 有没有等价于 zlib 的 Z_SYNC_FLUSH / Z_FULL_FLUSH 的能力？
   （Z_FULL_FLUSH 才会重置 32 KB 历史窗口；SYNC_FLUSH 只做字节对齐。）
3. 一个实例压完一段之后，能否复位再压下一段（deflateReset 语义）？
   还是必须 new 一个新实例？
4. 它产出的流是 raw deflate（wbits=-15）还是带 zlib 头？结尾是否置 BFINAL=1？

然后根据答案，给出两条拼接方案的可行性判断：
  方案 A：一块一个编码器实例，块间用 sync/全 flush 分隔，字节对齐后直接拼接。
  方案 B：一块一个完整独立 deflate 流（BFINAL=1），把除最后一块外的 BFINAL 位清 0 再拼
          （deflate 是位流，需要定位每块最后一个 block header 的位偏移）。

输出一份 200 字以内的结论：推荐哪条方案、理由、以及你不确定的是什么。
不要写实现代码。
```

### 5.2 P1-b：拼接 spike（200 行以内，只验证不落地）

```
【阶段 P1-b：拼接可行性 spike】

按 P1-a 推荐的方案，写一个独立的 200 行以内的小程序（放在 build/verify-codecs 或临时目录，
不要进产品代码），做一件事：

  用 N 个独立的 Deflate 编码器实例各压一块数据，按选定方案拼成一条 deflate 流，
  然后用【至少三个独立实现】解回来并逐字节比对：
    1. 7-Zip 本体（用 azcore 或本机 7z.exe 解一个真的 .zip）
    2. Python 的 zlib.decompressobj(wbits=-15)
    3. Windows 资源管理器 —— 这一条必须真的做：生成一个 .zip，用 Shell.Application
       或资源管理器真的解压一次，确认不报"压缩文件夹无效"

N 取 {2, 4, 8}，块大小取 {256KiB, 1MiB, 4MiB}，数据用 P0 生成的确定性数据集。

报告：
  - 三个解压器是否都通过（是/否，逐个列出）
  - 拼接后与"单线程压同一份数据"的产物大小差多少个百分点
  - 吞吐提升多少倍
  - 如果有失败组合，精确描述失败在哪个 N / 哪个块大小

不许修改 native/src 下的任何产品代码。
```

### 验收判据（P1-b）
- **三个解压器全部通过**，包括 Windows 资源管理器。
- 压缩率损失 **≤ 5%**（超过就说明块太小或窗口没处理好，回去调块大小）。
- 8 线程下吞吐提升 **≥ 3×**。

### 否决门槛（P1-b）
任一解压器失败，或提升 < 3× → **停止 P1**，把失败组合写清楚，转 P2（换编码器）或直接收尾。

### 5.3 P1-c：正式实现

```
【阶段 P1-c：把块级并行落进门面】

原则：
```

## 6. 阶段 P2 — 换更快的 Deflate 编码器（libdeflate / ISA-L）

### 目标
把 ZIP 用的 Deflate 编码器换成 libdeflate 或 ISA-L，预期 2–4×。格式不变。

### 6.1 P2-a：撞名优先级实验（必须先做）

```
【阶段 P2-a：codec registry 撞名行为的小实验，不许写产品代码】

背景：ZIP 的 Deflate 编码器是经 codec registry 取的（ZipAddCommon.cpp →
CPP/7zip/Common/CreateCoder.h 的 CreateCoder_Id），不是硬编码 new。
我想注册一个同 method ID 的替换实现，但上游查找顺序我不确定。

做一个最小实验：
1. 读 CPP/7zip/Common/CreateCoder.cpp 与 Codecs 注册相关代码（CPP/Common/RegisterCodec.*
   与 CPP/7zip/Common/*），弄清 FindMethod / CreateCoder_Id 在【多个 codec 声明同一个
   MethodID】时的选取规则：是取第一个？最后一个？还是报错？
2. 写一个临时验证（可以是一个只打印名字的小目标，不进产品）：注册两个同 ID 的 codec，
   打印实际被选中的是哪一个；再交换注册顺序，看选中结果是否随之改变。
3. 顺带确认：注册顺序是由什么决定的（链接顺序？静态初始化顺序？g_Codecs 数组插入次序？）

输出结论：
  - 同 ID 撞名能否稳定地让我的实现胜出？如果能，要怎么做才稳定？
  - 如果不能（例如取决于链接顺序，脆得不能依赖），给出替代方案：
    (a) 在门面层绕过 registry，直接实例化我的编码器（代价：要动 ZipAddCommon 之外的接线）
    (b) 放弃替换，回到 P1 的块级并行
```

### 6.2 P2-b：实现

```
【阶段 P2-b：接入 libdeflate 作为 Deflate 编码器】

前置：P2-a 已经确认能让新实现稳定胜出。

1. vendor libdeflate 到 native/third_party/codecs/libdeflate（BSD 许可），
   更新 native/third_party/MANIFEST.json 记录来源与许可。
2. 在 cmake/codecs.cmake 里加一个开关（照现有 zstd/lz4 的写法），默认 OFF，
   产品构建（build.ps1 / ci.ps1）显式打开。
3. 照 ZstdForkEncoder 的范本写一个 NCompress::NLibDeflate::CEncoder：
   实现 ICompressCoder + ICompressSetCoderProperties，接进 codec registry。
   注意：命名空间与文件名都要与上游不撞（ZstdFork 当年就是这么处理的）。
4. 级别映射：把 az_create_options.level (0..9) 映射到 libdeflate 的 1..12，
   在代码里写清楚映射表与理由，不要拍脑袋。
5. 逐字节验证：new 编码器压出来的 zip，必须能被 7-Zip、WinRAR、Windows 资源管理器、
   Python zipfile 打开并解出一致的字节。四家都要真的试。
6. 跑完整门禁：pwsh native/scripts/build-windows.ps1 -ExtraCodecs -RunTests
                 pwsh ci.ps1 -Static
```

### 验收判据
- 四家解压器全部通过 + 逐字节一致。
- 重跑 bench.ps1，ZIP/Deflate 吞吐相对 P0 基线 **≥ 2×**，压缩率不得劣化超过 2%。

### 否决门槛
提升 < 2×，或任一解压器不兼容 → **回滚，删除开关，不留死代码**。

### 结论（2026-10-18，量完决定不做）

读数在 `docs/perf-p2b-libdeflate.md` / `docs/perf-libdeflate.tsv` / `docs/perf-zlib-ng.tsv`，
探针在 `native/tests/probe/build-and-run-libdeflate.ps1` 与 `...-zlibng.ps1`（两份库都 clone 到
`build/` 下，仓库里不留副本，产品构建一行不碰）。

**停的原因不是速度**：libdeflate 在 `mixed` 128 MiB 上标准档那一格是 **334.6 MB/s / 0.30264**，
引擎是 25.3 MB/s / 0.30332 —— 门槛要 2 倍，实测 13.2 倍，而且产物还更小。**停的原因是形状**：
它的 compressor 只有 `alloc / compress(整块) / bound / free`，没有流式入口
（`libdeflate.h:59-160`；上游 README `:122` "There is currently no support for streaming"、
`:127-129` "if your application compresses large files as a single compressed stream … then
libdeflate isn't for you"）。而第 5.1 节 P1-a 的判词早就把选型标准写死了：
**看有没有 SYNC_FLUSH，不是看谁跑得快**。ZIP 的一个条目就是"一条流吃下一个大文件"，
用 libdeflate 只能切块再把 BFINAL 位拼起来 —— 那是 P1-a 判过"代价与收益不匹配"的那条路。

**这一节的另一半留给一次选型改动**：形状过关的那个库（zlib-ng：`Z_SYNC_FLUSH` /
`Z_FULL_FLUSH` / `deflateSetDictionary` 都在公开面上）同一份语料量到 **346 MB/s / 0.30276**
（5 级），而切与不切的产物字节数一样（只有 1 级差 2 字节）—— 速度这一关它同样超出门槛一个数量级。

## 9. 阶段 P5 — 7z 侧的字典 / 块旋钮

```
【阶段 P5：7z 的字典大小 ↔ 并行块数权衡】

LZMA2 的多线程块数与字典大小挂钩：字典小 → 块多 → 并行度高但压缩率低。
az_create_options.dict_size_mib 已经暴露了。

1. 量出 7z/LZMA2 在 dict = {16, 32, 64, 128, 256} MiB 下的 (MB/s, 压缩率)。

3. 如果结论支持，在 ArchiveCreationSettings 里让字典随级别档位自动取值，
   而不是永远用默认值。改完同步测试。

同样：先给建议表，确认后再改代码。
```

### 读数（5.8.0：字典那一半在 5.6.0，块这一半现在才做）
用户报"7z 完全是单线程在跑，设了压缩核心数也没用"，量的结果正是这一节的第二句话：
**并行度不是被线程数卡住的，是被块数卡住的**。标准档字典 32 MiB ⇒ 自动块
`clamp(字典 << 2, 1 MiB, 256 MiB) = 128 MiB` ⇒ 一份 128 MiB 的输入正好一块 ⇒
`mt=16` 下发到引擎也只有 1.38 个核在跑。同一个入口把块压到 4 MiB：**9.05 s → 1.28 s，
1.38 核 → 12.52 核**，产物 35 641 550 → 36 713 343 字节（大 3.0%）。
所以产品里改成：7z/LZMA2 的快速与标准两档按 `ceil(总量 ÷ (2 × 线程数))` 下发块大小
（`NativeEngine.TierExtras`），极速本来就自动切满（13.38 核）不动，极限要收那 3.0%
的体积、它的承诺是最小，也不动。全部读数、复现命令与不做的部分在 `docs/perf-mt.md`，
原始表 `docs/perf-mt.tsv`（脚本 `tests/perf/mt.ps1`）。
