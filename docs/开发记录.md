# Andzip —— 开发记录

> **这份是维护者读的深度文档**，不是入口。项目是什么、怎么构建、能做什么，看根目录的
> [`README.md`](../README.md)。这里保留的是**架构决策的推导过程、踩坑的症状与定位、
> 逐版本的验证记录，以及完整的已知限制清单** —— 这些东西放进入口文档会把人淹死，

> 内容背景：本项目把 `src/Andzip.Core` 的实现从 `System.IO.Compression` + SharpZipLib
> 整体换成了 `native/`（原样 vendor 的 7-Zip 引擎 + 一层扁平 C ABI）。
> 下面不少章节就是围绕这次换引擎展开的。

## 三、架构：接缝放在哪里

分层是**单向**的，界面永远看不到 native 的类型：

```
  Andzip.App（Avalonia 界面）
        │  只调用 Andzip.Core 的门面与选项记录
        ▼
  Andzip.Core  ◀── 深模块：小的接口 + 大量实现
        │  Archive/NativeEngine.cs 是唯一出口
        ▼
  Andzip.Native（P/Invoke 外壳，ArchiveReader / ArchiveWriter / Hasher）
        │  41 个 az_* 函数，UTF-8，__cdecl，不透明句柄
        ▼
  andzip_core.dll / .so / .lib（7-Zip 引擎）
```

### 为什么接缝放在 Core 的门面上

`ArchiveCreator` / `ArchiveExtractor` / `ArchiveReader` / `ArchiveTester` 四个静态门面
+ 一组选项/结果记录，就是界面需要的全部接口。换引擎时**界面一行都不用改**（本次只为了
进度条和格式表动了少量调用点）。这就是深模块的意义：接口一小段，实现里塞进 60 种格式、
7 种可写格式、25 个编解码器、加密、分卷、路径安全。

### 职责划分：引擎解码，Core 决定落盘

这是本次重构最关键的一条设计判断：

- **引擎负责**：识别格式、解码、编码、CRC 校验、固实块的一次性解码、7z 风格
  （`archive.7z.001`）多卷的自动拼接。
- **Core 负责**：条目命名、是否包含根目录、排除 `Thumbs.db`、不自我包含、重名策略
  （询问 / 覆盖 / 跳过 / `name (2).ext` 自动重命名）、非法文件名字符清洗、
  zip-slip 防护、单顶层目录剥离（解压的三情形）、WinZip 风格（`.z01`）分卷的切块与拼接。

理由：native ABI 的重名策略只有「覆盖 / 跳过 / 引擎自定的 `~1` 重命名」，表达不了参考
软件的「逐个询问」和 `name (2).ext`；而路径安全、命名规则本来就该由应用侧统一掌控。

### 解压的两条落地路径（有意为之，不是冗余）

- **整包原生解压**（默认）：一次调用，固实（solid）归档只解码一次。
- **逐条解压**：只有当本次确实需要改名、清洗非法字符或剥离顶层目录时才走 —— 因为那时
  目标文件名已经和归档里存的不一样，整包解压无法表达。

代价是固实归档逐条读会重复解码，所以判定条件收敛在 `ExtractionPlan.NeedsPerEntry`
一处，能走快路就走快路。

### 错误模型：翻译，而不是透传

`NativeEngine.Translate` 把引擎错误码映射到 Core **原有**的异常类型，界面既有的 catch
分支在换引擎后依然成立：

| 引擎结果 | Core 异常 | 界面处理 |
|---|---|---|
| `ErrorNotFound` | `FileNotFoundException` | 通用错误框 |
| 打开阶段的 `ErrorBadFormat` | `ArchiveConstraintException(FormatNotSupported)` | 「不支持的格式」（本地化） |
| 读取阶段的 `ErrorBadFormat` / `ErrorCrc` | `InvalidDataException` | 通用错误框 |
| `ErrorUnsupported` | `ArchiveConstraintException` | 「暂未实现」 |
| `ErrorPassword` | `ArchiveFailureException(Password)` | 通用错误框 |
| `ErrorCancelled` | `OperationCanceledException` | 静默返回 |

`Andzip.Native.AndzipException` 不会从 Core 漏出去 —— 否则 P/Invoke 的错误码就成了
界面必须知道的契约。

## 四、怎么构建

### 0. 前置

- Visual Studio 2022/2026 的 C++ 工作负载（引擎用）；CMake / Ninja 用 VS 自带的即可。
- .NET 10 SDK。
- 交叉编译 Linux 时需要 Zig（`native/scripts/provision-toolchain.ps1` 会下载便携版）。

### 1. 先构建压缩内核

```powershell
pwsh native/scripts/build-windows.ps1 -RunTests
# 本机只有 Windows PowerShell 时：
powershell -ExecutionPolicy Bypass -File native/scripts/build-windows.ps1 -RunTests
```

脚本会：导入 `vcvarsall` 环境 → 配置并编译 `andzip_core.dll`（约 284 个编译单元，几分钟）
→ 跑 532 条原生断言 → 用 `check-exports.ps1` 核对导出符号恰好是头文件里的 41 个 `az_*`
→ **把 DLL 暂存到 `src/Andzip.Native/runtimes/win-x64/native/`**。

最后一步是界面工程能找到引擎的前提；缺了它，`dotnet build` 依然成功，但运行时会提示
"compression engine unavailable"。

### 2. 构建界面与业务层

```powershell
dotnet build Andzip.slnx -c Release
```

`Andzip.Core` 引用 `src/Andzip.Native`，后者把 `runtimes/**` 下的原生库带到输出，
所以 `src/Andzip.App/bin/Release/net10.0/runtimes/win-x64/native/andzip_core.dll` 会自动出现。

### 3. 跑测试

```powershell
dotnet test Andzip.slnx -c Release                                    # 317 个用例（xUnit）
dotnet run --project src/Andzip.Native.Tests -c Release      # 69 条断言（控制台自检）
```

第二条**必须单独跑**：`Andzip.Native.Tests` 是不带 xUnit 适配器的控制台程序，
`dotnet test` 对它只会还原、不会运行。`build.ps1` 已经把两条都放进门禁里。

### 4. 运行

**命令行（推荐，可复现）**：

```powershell
powershell -ExecutionPolicy Bypass -File run.ps1        # 构建 + 启动主程序
powershell -ExecutionPolicy Bypass -File run.ps1 -Check # 只构建 + 跑两套测试，不开窗口
```

`run.ps1` 不依赖任何 IDE 状态，并且会先确认 `andzip_core.dll` 真的在
`src/Andzip.Native/runtimes/win-x64/native/` 里 —— 缺了就直接报错并给出重建命令，
而不是等程序起来后显示「压缩引擎不可用」。（等价的裸命令是
`dotnet run --project src/Andzip.App`。）

**在 Visual Studio 里按 F5**：双击 `Andzip.slnx` 打开后直接 F5 就能起主程序 —— 解决方案里字典序
第一项是 `src/Andzip.App/Andzip.App.csproj`，而 VS 在没有 `.suo` 状态时正是按**项目路径字典序**
选默认启动项目的（C# 外壳工程因此从 `native/csharp/` 移到了 `src/` 下，理由见第七节第 12 条）。

如果仍报「无法直接启动带有『类库输出类型』的项目」，看工具栏上启动项目下拉是不是 `Andzip.Native`：
那是**本地 `.vs\` 里残留的旧状态**（本次修复之前留下的），删掉 `Andzip\.vs\` 重新打开即可；
或者手动 `Andzip.App → 右键 → 设为启动项目`。交付目录里已经没有 `.vs\`。

**别搞混这几个 exe**（这是刚踩过的坑）：

| 路径 | 是什么 |
|---|---|
| `dist/Andzip-v<版本>-win-x64.exe` | **主程序**（单文件绿色版，交付物） |
| `src/Andzip.App/bin/<配置>/net10.0/Andzip.exe` | 主程序，未打包的开发版 |
| `build/native/bin/azgui.exe` | **不是主程序**：内核自带的最小验证界面，标题栏写「Andzip 压缩内核验证界面」 |
| `build/native/bin/azcore.exe` | 内核命令行工具（`list` / `create` / `extract` / `test`） |
| `src/Andzip.Native.Tests/bin/.../Andzip.Native.Tests.exe` | 69 条断言的控制台自检 |

标题栏应显示 `Andzip (Professional) — 7-Zip 26.04 (x64) · Release · 60 formats / 7 writable`。
**如果显示 `compression engine unavailable`，就是第 1 步没做或没暂存成功。**

### 5. 打包单文件绿色版

打包体积的实测结论（别再重复试错）：

| 开关 | 结果 |
|---|---|
| 自包含 + `PublishTrimmed` + `TrimMode=full` + `EnableCompressionInSingleFile` | 19.72 MB（基线） |
| 再加 `DebuggerSupport=false` + `EventSourceSupport=false` + `MetadataTrimming=complete` | **19.47 MB** ✅ 已进 `build.ps1` |
| 改框架依赖（`--self-contained false`） | ❌ **25.18 MB，反而更大**：不能裁剪，而 Skia / ANGLE / HarfBuzz / 内核这些原生库占了大头且单文件包里压不动 |
| `UseSystemResourceKeys=true` | ❌ 体积零收益，还会把框架异常文案换成资源**键**，而错误框是直接显示 `ex.Message` 的 |
| 手工摘掉 `mscordaccore` / `mscordbi` / `DiaSymReader` | ❌ 后两个本来就不进 bundle，实测差 30 字节，不值得为它加一个 MSBuild target |

#### 包内体积到底花在哪（2026-10-12 实测，v0.9.3）

未打包 41.39 MB / 72 个文件，压成单文件后 19.50 MB：

| 部分 | 未压缩 | 占比 |
|---|---|---|
| 渲染栈：`libSkiaSharp` 8.98 + `av_libglesv2`(ANGLE) 5.17 + `libHarfBuzzSharp` 1.72 | 15.87 MB | 38% |
| .NET 运行时：`coreclr` 4.40 + `clrjit` 2.00 + `System.Private.CoreLib` 2.23 + hostfxr / hostpolicy / gc … | ≈12 MB | 29% |
| 调试用原生库：`Microsoft.DiaSymReader.Native` 2.27 + `mscordaccore` ×2 2.58 + `mscordbi` 1.18 | 6.03 MB | 14%（单文件包里基本已不带） |
| Avalonia 与本项目托管 DLL | ≈4 MB | 10% |
| **`andzip_core.dll`（7-Zip 内核 + C ABI）** | **1.67 MB** | **4%** |

**结论：这个体积不是链接库形式造成的。** 我们的 C/C++ 内核只占 1.67 MB —— 与「7-Zip 本体不到 2 MB」
是同一个量级；多出来的 17 MB 是 .NET 运行时与 Skia 渲染栈。C++ 代码编译产物必须是机器码二进制，
要么 `.dll` 要么 `.lib` 链进某个可执行文件，换一种形式不会让代码消失。唯一「不带独立二进制」的路子是
NativeAOT，但 Avalonia + 大量 P/Invoke + 7-Zip 的 COM 代码在 AOT 下是另一个量级的工程，而且产物通常
**更大**（IL 换成机器码，一般 25–40 MB）。另外 `andzip_core.dll` 是**故意**以独立文件存在的：同一份内核
要被 `azcore`、`azgui` 与托管三侧复用，见第七节第 13 条。

真能压的三条路，以及为什么不选（2026-10-12 与用户确认：接受现状，继续做功能）：

| 方案 | 能到 | 代价 |
|---|---|---|
| 去掉 ANGLE，渲染退回软件 / 原生 GL | ≈17 MB | 实测删掉 `av_libglesv2.dll` 后能正常启动，但流畅度与显示要人眼确认 |
| 框架依赖（不打包 .NET 运行时） | 目录 25.28 MB / zip ≈12 MB | 用户机器必须装 .NET 10 Desktop Runtime，不再是免安装绿色版 |
| 换 UI 技术栈（Win32 + comctl32，内核静态链入） | 2–3 MB | 等于重写整个界面层，现有 Avalonia 代码作废 |

**19.5 MB 是「免安装 + 不挑机器 + 带 GPU 渲染」这个组合的正常代价**，在换掉其中任何一项之前不再优化体积。


```powershell
pwsh build.ps1                 # 版本号 → 单元测试（不过就拒绝打包）→ 发布 → 体积核对
pwsh build.ps1 -SkipTests      # 仅调试
```

产物 `dist/Andzip-v<版本>-win-x64.exe`，约 19.7 MB（体积预算 ≤ 25 MB）。

> 打包有一个必须记住的坑：`andzip_core.dll` 是以「内容项」的形式进入输出的，不是 RID
> 资产，所以 `IncludeNativeLibrariesForSelfExtract` **不会**把它打进单文件包，必须用
> `IncludeAllContentForSelfExtract=true`。`build.ps1` 里已加注释，并且发布后会扫描产物
> 字节确认 `andzip_core.dll` 真的在里面 —— 这个失败只在运行时才暴露，不能靠人记得。

### 6. 交叉编译 Linux（可选）

见 `native/README.md`：用 Zig 作交叉驱动，`x86_64-linux-gnu` / `aarch64-linux-gnu` 动态库
与 `x86_64-linux-gnu` 静态库都能从 Windows 主机编出来。想一次性把「Windows 动态 + Windows
静态 + Linux 三个目标」全过一遍并核对导出符号：

```powershell
powershell -ExecutionPolicy Bypass -File native/scripts/verify-all-targets.ps1
```

它按平台依次打印每一步的结果（编译、断言数、导出核对），任何一步失败都会抛错中止。
（这句「会抛错」是修出来的，不是天生的：早期版本只检查 `$LASTEXITCODE`，而可执行文件找不到时
`$LASTEXITCODE` 压根不更新，于是 Linux 三个目标整段没跑、脚本却报全绿 —— 见第七节第 14 条。）

### 7. 持续集成（CI）

门禁本体是 **`ci.ps1`**，本地和 CI 跑同一份 —— 这样「CI 绿」和「我机器上绿」是同一个命题，
不会出现只在流水线里才跑的隐藏步骤：

```powershell
powershell -ExecutionPolicy Bypass -File ci.ps1                          # 完整门禁
powershell -ExecutionPolicy Bypass -File ci.ps1 -Static                  # 再加静态库链接（CI 用这个）
powershell -ExecutionPolicy Bypass -File ci.ps1 -SkipEngine -NoPackage   # 只跑托管侧，最快
```

`.github/workflows/ci.yml` 三个作业：

| 作业 | 跑什么 | 是否卡门禁 |
|---|---|---|
| `windows` | `ci.ps1 -Static`：532 原生断言 ×2 种链接 + 41 导出核对 + 235 xUnit + 69 自检 + 打包，上传绿色版与内核二进制 | ✅ 失败即红 |
| `linux` | `build-unix.sh -T`：**在真 Linux 上执行** `andzip_core_tests`，再核对导出符号 | 原生层 ✅；托管层仅报告 |
| `macos` | `build-unix.sh -T`，内核从未在 macOS 上编译过 | 仅探测（`continue-on-error`） |

两个刻意的取舍，别顺手改掉：

- **托管测试在 Linux 上是 `continue-on-error`**。这 317 个用例从没在非 Windows 上跑过，里面
  有按 Windows 语义写的路径清洗断言（`<>:"|?*` 在 Linux 上是合法文件名字符）。先让它把真实
  结果报出来，读过之后再决定要不要升格成门禁 —— 直接开成硬门禁只会得到一片红，然后被人关掉。
- **Windows 作业用 `shell: powershell`（Windows PowerShell 5.1）而不是 `pwsh`**。仓库里的
  `.ps1` 都是按 5.1 写的并保持纯 ASCII，换 pwsh 等于换一个没验证过的执行环境。

要真正跑起来还差一步：**这个目录目前还不是 git 仓库**，所以 workflow 不会被触发。

```powershell
cd Andzip
git init -b main
git add .
git commit -m "Andzip: self-contained deliverable (native engine + Avalonia app)"
git remote add origin <你的仓库>
git push -u origin main
```

`.gitignore` 已备好：`build/`、`dist/`、`bin/`、`obj/`、`.vs/` 一律不入库（约 740 MB 可再生
内容）。**唯一被跟踪的原生二进制**是 `src/Andzip.Native/runtimes/win-x64/native/andzip_core.dll`
—— 少了它，托管侧作业没有引擎可加载，CI 的构建 / 测试 / 打包三步会全红。

## 五、已完成的功能

### 压缩（新建压缩文件对话框，FR-2）

- **可创建格式 7 种**：`7z`、`zip`、`tar`、`tgz`、`gz`、`bz2`、`xz`（`wim` 引擎支持但界面
  暂未列入）。旧实现只有 ZIP / TAR / TGZ / GZ。
  **0.11.0 起下拉框按运行时的 `CanCreate` 过滤**（`ArchiveFormatOption.Creatable`）：
  参考软件那 12 项候选里有 5 项（ZIPX / EXE / LZH / ISO / ZPAQ）我们只能读不能写，
  选中之下只能开始一句「该功能暂未实现」。摆一个点下去必定失败的选项是骗人的，
  所以从列表里撤掉；这五项仍留在 `All` 里供扩展名归类使用。
- **「文件名」默认值跟着选中的东西走**（0.11.0）：压一个 `photo.jpg` 得到的是同目录的
  `photo.zip`，一次压多个（或还没有输入）才叫「新建压缩」，目录取它们的共同父目录，
  各不相同才退回「设置 → 压缩 → 输出目录」。规则在 `ShellTasks.SuggestedArchivePath`，
  对话框与右键「压缩到…」、拖进主窗口那三条入口共用一份。
- 压缩级别 5 档（仅存储 / 极速 / 快速 / 标准 / 极限）映射到引擎的 0..9 级。
- 每格式独立的压缩方法表：ZIP 可选 Deflate / Copy / BZip2 / LZMA / LZMA2 / Deflate64 / PPMd，
  7Z 可选 LZMA2 / LZMA / PPMd / BZip2 / Deflate / Copy。方法表来自引擎实测，不是抄规范。
- 密码 + 加密算法：ZIP 支持 ZipCrypto 与 WinZip AES-256，7Z 支持 AES-256 与「加密文件名」。
- 分卷（ZIP）：WinZip 风格 `name.z01 … name.zip`，档位与参考软件一致，支持自定义 MB。
- 复选项：压缩后测试、压缩后删除源文件、每个输入单独成包、是否包含根目录、排除 Thumbs.db。
- 输出文件在输入目录内时不会自我包含。
- **进度上报**（新增）：字节数、总量、当前条目、百分比；界面从「不确定进度条」变成真实
  百分比条。
- 引擎忽略某项设置时通过 `ArchiveCreationResult.Warnings` 回传，界面显示而不是丢弃。

### 解压（FR-3）

- **可读格式 60 种**：zip / 7z / tar / gz / bz2 / xz / zst / rar / cab / iso / nsis / wim /
  chm / apfs / ext / fat / ntfs / udf / squashfs / dmg / vhd / vhdx / rpm / arj / lzh …
  格式由引擎**按内容嗅探**，不再靠扩展名 switch，所以没有扩展名或扩展名写错的包也能打开。
- 重名策略：询问（回调）/ 覆盖 / 跳过 / 自动重命名 `name (2).ext`。
- 非法文件名字符清洗（`<>:"|?*` 与控制字符 → `_`），结尾的点与空格也显式处理。
- **「选择解压路径」对话框不画目录树**（0.11.1）。原来右边那块是手写 `TreeView`，
  而且它**根本展不开** —— `ItemTemplate` 是扁平的 `FuncDataTemplate`，没把
  `FolderNode.Children` 绑成子项来源，所以连展开三角都不出现，界面上永远只有 `C:\` `D:\`。
  参考软件那块是系统 shell 树（`SysTreeView32`），**嵌不进 Avalonia 的窗口**，
  于是浏览统一交给 `IStorageProvider.OpenFolderPickerAsync`（Windows 上就是
  `IFileOpenDialog` 的选文件夹模式），并把 `SuggestedStartLocation` 设成当前目标路径 ——
  以前它从"我的文档"开始翻，而用户其实只想往下走一层。
  快捷位置改成横排一行，窗口 760×560 收到 700×292。
- zip-slip 防护：条目路径跳出目标目录时**抛异常**，不静默跳过。
- 解压的落点：所有条目共用同一个顶层目录时才剥离那一层；顶层同时有文件与目录时不剥。
- 保留修改时间；空目录也会创建。
- 解压后删除压缩包（在归档句柄释放之后才删，避免删不掉）。
- 「只校验 CRC 不解压」（完整性测试）覆盖全部 60 种格式。
- 加密包识别更准：头加密的 7z 连打开都需要口令，这种「打开即失败」也被判定为需要口令。

### 首页与主工具栏（FR-1）

- 首页不再是「两张卡片」的欢迎页，而是与压缩包视图**同一套双栏骨架**的空状态：左树栏 +
  分隔条 + 右内容栏 + 底部栏。打开与关闭压缩包时窗口布局不跳。
- 蓝色主工具栏：打开 / 解压 / 新建 / 添加 / 删除 / 测试 / 扫描 / 查看 / 当前语言。
  已接命令的才亮着，其余是禁用态而不是假装有响应。
  「打开」「解压」右侧原本各挂一个下拉箭头，0.10.0 删了 —— 「打开」的菜单里那条
  「最近的文件」当时根本没有这个功能、永远灰着，「解压」的菜单里那一条又与主按钮同命令，
  两个箭头点开都看不出差别。（「最近的文件」后来在 0.12.0 做成了 `文件 → 最近的文件`
  子菜单 —— 它本来就该住在菜单里，而不是工具栏的一个下拉里。）
- **拖进主窗口的东西**（0.11.0）：单个、且扩展名是引擎读得开的包 → 就在这个窗口里打开
  （与右键「用 Andzip 打开」是同一条任务）；其余（普通文件、文件夹、一次拖多个）→
  开「新建压缩文件」对话框并把它们填进输入列表。判断在 `ShellTasks.RouteDroppedPaths`，
  与右键共用语汇。
  这**不是**"加进当前打开的包里" —— 往已有归档写成员做不到（见第六节）。
  接收端用的是 11.3 的新数据接口（`e.DataTransfer` + `DataFormat.File` + `TryGetFiles()`），
  旧的 `IDataObject` / `DataFormats.FileNames` 已经过时；`IStorageItem` 挡第三方实现，
  所以这一层没有自动化测试（第七节第 21 条）。
- 菜单与工具栏共用同一批命令委托（`MainMenuModel` 的 CommandId），不重复实现第二套分发。
- **`文件 → 最近的文件`**（0.12.0）：最多 10 条、最新在前、不区分大小写去重，
  点一条就在当前窗口打开它，底下带「清除最近使用的文件记录」；一条都没有时摆的是
  禁用的「（尚无记录）」而不是空菜单。规则全在 `Core/Settings/RecentFiles.cs`（纯逻辑、单测）。
  三条要紧的决定：**打开成功才记账**（失败的包与被取消的口令不该出现在"点开就能再看一次"的
  菜单里）；**子菜单每次展开时重建**（建菜单时填一次的话，用户打开第一个包之后它还是空的）；
  **文件没了那条自己消失**（展开时先 `Prune` 再读）。
  存储用 `settings.ini` 的 `recent_files`，分隔符是 `|` 而不是 `AppSettings.GetStringList`
  那套 `;` —— 分号在 Windows 文件名里合法，会把一条记录劈成两条，所以这里刻意没有"顺手统一"。
- **`文件 → 另存为 / 删除压缩文件 / 永久删除压缩文件 / 打开压缩文件位置`**（1.3.0）。
  四条都只在**正开着压缩包**时可用，靠的不是"点击时才发现不能做"：菜单项建的时候把 CommandId
  写进 `Tag`，切换视图时按 `MainMenuModel.ArchiveOnlyCommands` 真的置灰，
  快捷键那条路径（`Ctrl+Del` / `Shift+Ctrl+Del`）也带同样的守卫。
  几个决定值得记：
  - **另存为是复制，不是重压**。重压要重新决定格式/级别/口令，那是「新建压缩文件」的活；
    而且原包里引擎写不出来的东西（非常规方法、ZIP 注释）重压一次就丢了。
    目标等于原路径时直接说明"没有做任何改动"，不做静默的自抄。
  - **删除走 `SHFileOperationW` + `FOF_ALLOWUNDO`**（`Services/RecycleBin.cs`），
    没有用 `Microsoft.VisualBasic.FileIO` 那个现成的壳 —— 它为这一个方法要拖进整个 VisualBasic
    程序集，裁剪发布下多一层不确定。`pFrom` 要求**双零结尾**，所以字符串手工 `StringToHGlobalUni`
    分配，而不是让 marshaller 处理含嵌入零的字符串（各版本说法不一，手工分配没有歧义）。
  - **两条删除都先弹确认框，且按钮上的词是「删除」不是「确定」** —— 确认框要替用户说出后果。
    `MessageWindow` 从此有两种形态：单钮（Esc/确定都是"知道了"）与双钮（Esc 归取消那一侧）。
  - **先关视图再删**：图标视图可能还开着包文件的句柄在读条目，那时删会失败，
    而失败原因（文件占用）看起来和用户的操作毫无关系。
  - 非 Windows 上**不悄悄退化成永久删除**：没有回收站可去就报错，
    因为那是把"还能反悔"的承诺在用户不知情时换掉，比报错严重。
  - **定位用 `explorer.exe /select,"路径"`，且必须拼成一条带引号的 `Arguments`**：
    `ArgumentList` 会让 explorer 收到整串 `"/select,C:\a b\x.zip"`，它认不出来，
    于是"打开了目录但没选中那个文件"，看着就像功能没生效。底部栏那个按钮与菜单项现在共用
    `Services/ArchiveReveal.cs` 这一份。
- **所有控件文案过一遍 `LangCatalog.Label`**（App 层的扩展，内部就是 `MnemonicText.Strip`）：
  语言包保留 Win32 的 `文件(&F)` 写法，而 Avalonia 的 SimpleTheme 不解析 `&`，
  不过滤就会显示成「文件(&F)」。0.9.11 只有菜单栏与工具栏调了剥离，对话框上的按钮
  全漏了（用户看到的正是「确定(&O)」），所以 0.10.0 把取文案的入口收成一个方法，
  并用两条"任何窗口都不许出现 `(&X)`"的界面测试钉住 —— 问的是渲染出来的文字，
  不是"某个键有没有被剥"，所以将来新增控件自动被覆盖。

### 压缩包视图（FR-4）

- **左侧目录树**：根节点是压缩包文件名，往下是包内目录。树由 `ArchiveHierarchy`（Core，
  带单元测试）从**扁平清单**重建 —— 很多 ZIP 只写文件路径、不写目录条目，照抄 `is_dir`
  为真的那些行会漏掉整层目录。子文件夹默认**收着**（根节点始终展开，不然整棵树是空的），
  要一次全摊开就在「设置 → 查看」里勾「自动展开树里的文件夹」。
- **右侧 11 列详情**：名称 / 压缩后大小 / 原始大小 / 类型 / 修改日期 / 压缩方法 / 加密算法 /
  循环冗余检验 (CRC) / 属性 / 注释 / 附加信息。表头可点排序（目录在前、文件在后，各自按名称
  码位序），`..` 恒在首行。**列宽可拖拽**（表头每列右边一条 5px 分隔列，松手后落到实例字段上
  再重画列表），窗口窄到放不下全部列时列表出自己的横向滚动条，表头按同一位移量反向平移对齐。
- **图标视图**：图像条目回读原始字节生成缩略图。`ArchiveContentSession` 只开一个归档句柄、
  串行读（引擎句柄不是线程安全的）、`Bitmap.DecodeToWidth` 直接缩到 128px；只在切到图标视图
  时才建立，切目录取消上一批请求，超过 400 条或单条超过 32 MB 就退回通用图标。
- **底部栏三个按钮**：详情列表 / 图标视图 / 在系统文件管理器里定位压缩包。状态文字是
  「文件: N, 文件夹: M, 压缩文件大小: X」，X 取引擎报告的包体物理大小。
- 点树节点与双击文件夹行 / `..` 行都汇到同一个导航入口。
- 名称列是「图标 + 文字」的两列 Grid，**不是** StackPanel：StackPanel 测量子项时给无限宽度，
  `TextTrimming` 永远不会触发，长文件名会直接压到隔壁列上。
- **打开流程**：系统文件框只列引擎报告的受支持扩展名（115 个，含 `.tgz` / `.txz` 这类副
  扩展名）；头加密的包在打开时就问口令（先试一次，引擎要口令才弹框，取消即放弃）。
- 命令行传入压缩包路径可直接打开 —— 这是文件关联的入口，也是没有扩展名的包的兜底路径。
- 条目方法从 ZIP 规范编号改成引擎方法名（`LZMA2:24`、`Deflate`、`Store`），
  不再有 `NoZipMethod = -1` 这种为 tar/gz 硬凑的占位值。
- 嵌套归档透明化：`.tgz` / `.tar.gz` / `.tar.xz` 自动展开内层清单，解压与测试同样按内层处理。
- 分卷读取：`archive.7z.001` 由引擎自动取回兄弟卷；WinZip 的 `.z01` 由 Core 拼接。

### 设置与文件关联（FR-5）

- **选项 → 设置（F5）**：`Views/SettingsWindow.cs`，左侧蓝色导航 + 右侧页面 + 底部「重置 / 确定」，
  导航顺序与参考软件一致（常规 / 文件关联 / 上下文菜单 / 解压 / 压缩 / 查看 / 安全 / 高级 / 语言）。
  九个页面**全部实装**：常规、文件关联、上下文菜单、压缩、解压、查看、安全、高级、语言。
- **常规页**（照参考软件的样式：小标题 + 左标签右控件）：
  - **解压过程中允许按 Esc 取消** → 关掉后进度窗口不吃 Esc，防止大文件解压到一半误触前功尽弃。
    「取消」按钮本身始终可用。压缩与解压共用这一项。
  - 这一页原来还有「双击压缩包文件时」那一项，**1.6.0 搬到解压页**了（见下面的解压页）：
    它选的落点规则与解压页第一条是同一件事，两页各留一份控件就是两个主人写同一个键。
- **后台任务（没有主窗口那一条路径）**：`App.TryResolveTask` 决定做哪件事 ——
  命令行带 `/task=…` 就照右键说的做；不带开关就是双击，看「解压 → 双击」设置。
  两条都**不创建主窗口**，只弹进度窗口（居中于屏幕、出现在任务栏），跑完或被取消自动关闭并结束进程。
  生命周期切到 `OnExplicitShutdown` —— 默认策略下没有主窗口会让进程立刻自己退出。
  - `extract`（右键**解压**，也是双击 + 「解压 → 直接解压」那条）：落点取决于包里装着什么，
    见下面的「解压的三情形」。加密包先问口令再开工，避免解到一半才报“要口令”留下一堆半截文件。
  - `extract-delete`（右键**解压并删除**）：与上一条同一个落点规则，只是成功后把包删掉。
    **分卷包连卷一起删**（`SplitVolumeSupport.EnumerateParts`）—— 只删主卷会留下一地读不了的 `.z01`，
    那比一个不剩更糟。删除失败不改变"解压成功"这个结论。
  - `compress-zip`：压到源路径的同名兄弟位置，用默认档位（正常压缩、无口令、不分卷）。
    **重名往后加序号**（`report (2).zip`），绝不覆盖已有的包 —— 右键是用户随手点的。
    取消或失败时不留半成品（`ArchiveOutputGuard`）。
  - `compress-dialog`：把「新建压缩文件」对话框开起来，输入列表与包名都预填好，用户点开始才压。
    这条**不自动收尾**：窗口关掉才 `Shutdown()` —— 用户可能看一眼就取消，也可能压完再改主意。
    口令 / 分卷 / 级别 / 选 7Z 这些需要人看着选的东西，静态动词表达不了，所以它是菜单里的第二条。
  - 任务枚举与命令行写法在 `Core/Archive/ShellTasks.cs`，落点的三情形在
    `Core/Archive/ExtractionLayout.cs`，都是纯逻辑、单测覆盖。
    老的 `auto-extract` / `extract-here` / `compress-7z` 命令行**仍然认**（`TryParse` 映射到
    今天最接近的那条）：动词键在写注册表时会被删掉，但用户桌面上可能还留着指向老命令行的快捷方式。
- **解压的三情形**（`ExtractionLayout`）：读一遍清单，只看顶层。
  | 包里顶层是什么 | 判定 | 解到哪儿 |
  |---|---|---|
  | 只有一个文件（`.gz` / `.xz` 这类单流包天然是这种） | `SingleFile` | 压缩包所在目录，直接得到那个文件 |
  | 所有内容都在同一个顶层文件夹里 | `SingleFolder` | 压缩包所在目录，整个文件夹放出来 |
  | 多个平级文件或目录混在一起（含空包） | `Mixed` | 新建以压缩包命名的文件夹收纳 |
  - 第二行是这条规则的价值所在：`docs.zip` 里装着 `docs/…`，再套一层 `docs\docs\` 是用户最烦的结果。
    0.9.12 之前它叫「智能解压」，与一条固定套同名文件夹的 `extract` 并存；现在只剩这一条，
    名字也就没有存在的必要了。
  - `Mixed` 时目标名被占用（**目录或文件都算**，同名文件一样会让建目录失败）就依次试
    `名称 (2)`、`名称 (3)`…… 与 `UniqueArchivePath` 不同，这里不把最后一段当扩展名剥掉：
    `photos.tar` 撞名要得到 `photos.tar (2)`，不是 `photos (2).tar`。
  - 需要先读清单，所以它排在口令之后（清单本身也在包里，加密头没有口令读不出来）。
- **文件关联页已实装**：35 项候选分成 压缩包文件 / UNIX / 其它 / CD/DVD 四组，候选集由
  `FileAssociationCatalog.Supported(引擎可读扩展名)` 过滤得出 —— 引擎读不了的格式不会出现在列表里，
  也就勾不出一个「关联了却打不开」的项。
- **勾选 = 双击就用 Andzip**：写 `HKCU\Software\Classes` 下每格式一棵 `Andzip.<id>` ProgID 子树，
  把 ProgID 挂进该扩展名的 `OpenWithProgids`（右键「打开方式」里能看到），**并把扩展名键的默认值
  指过来**（双击才真的走我们）。两处缺一不可 —— 只挂 `OpenWithProgids` 的话，双击照旧用原来的
  默认程序，这正是第一版“点了没生效”的原因。
- **撤销是可逆的，不是猜的**：覆盖默认值之前先把原值记进 `settings.ini`（`AssociationOriginals`，
  `扩展名=ProgID` 列表），取消勾选时按记录还原；当时根本没有默认值的就删掉那个值。只还原
  「现在还指着我们」的扩展名 —— 期间被别的软件改过就不动它。
- **Windows 的默认应用保护改不动，也不硬改**：`FileExts\<ext>\UserChoice` 里的哈希是用每用户随机
  密钥算的，伪造它属于绕过系统安全机制，而且随版本更新随时失效。
- **但「已关联 ≠ 双击就走我们」，这一层必须显说出来**：这台机器上实测到的就是这种情况 ——
  `.7z` 的 `HKCU\Software\Classes\.7z` 默认值已经是 `Andzip.7z`，ProgID 三件套也齐全，
  可 `UserChoice` 里仍然写着 `Bandizip.7z`，而 **UserChoice 的优先级更高**，于是双击开出的还是 Bandizip。
  以前只写 `HKCU\Software\Classes` 的话，设置页那个勾是亮着的，用户完全看不出哪里不对。
  现在关联页会把这类扩展名列成一红条（`ShadowedDefaults`）并给出「设为默认…」按钮，
  点了直接跳到 `ms-settings:defaultapps?fileExtension=.7z`；登记时新挡下的那些更是当场跳过去，
  不只弹一句提示。系统里从没手动指定过默认程序的扩展名（本机的 .zip / .rar / .tar / .gz 属于这种）
  没有 UserChoice，写 `HKCU\Software\Classes` 就直接生效。
- **列表显示的是系统真实状态**：打开设置时逐项问注册表（`IsRegistered`），不拿 `settings.ini`
  当答案。设置文件记的是「上次写成功的那批」，而注册表会被别的软件改、被清理软件清、被用户手动
  撤销 —— 照它回显就会显示一堆勾着但实际没生效的项，用户再点「应用」也看不出自己已经点过了。
  「重置」= 重新读一遍系统状态。
- 「立即应用」只在勾选与系统实际状态不一致时可用；「确定」会顺手应用未保存的改动再关窗，
  右上角 X 才是放弃改动。「Windows - 设置默认程序」打开 `ms-settings:defaultapps`。
- 目录刻意不含 APFS / NTFS / ELF / PE(dll,sys) / VHD 这类「能嗅探出来但不是压缩包」的格式，
  也不含 Compound（它的扩展名是 doc / xls / ppt）。**它们仍然能打开** —— 打开对话框与命令行走的是
  内容嗅探，与关联表无关。
- 设置存储是扁平 `key = value` 文本（`Andzip.Core.Settings.AppSettings`），落在
  `%APPDATA%\Andzip\settings.ini`。没用 JSON：反射式序列化在 `PublishTrimmed` 下要额外保留配置，
  为一堆标量不值当；而且语言包与 VersionNo.ini 本来就是这套语法。
- **上下文菜单页**（`Services/ContextMenuService.cs` + `Services/FileAssociationService.cs`）三个开关：
  - **为所有文件添加「压缩为」菜单项** → 写 `HKCU\Software\Classes\*\shell\Andzip.compress-*`，
    两条：`compress-zip` / `compress-dialog`（打开「新建压缩文件」对话框，7Z 在那里选）。
    两条都带一个 `AppliesTo` 值，让它们在压缩包扩展名上隐身 —— 见下面「动词隐身」。
  - **为文件夹添加「压缩为」菜单项** → 写 `…\Classes\Directory\shell\Andzip.compress-*`，
    不带 `AppliesTo`（文件夹没有扩展名，本来也不该被过滤）。
    两个范围各写各的，所以只勾一个时文件夹（或文件）上不会出现另一项。撤销就是删掉带
    `Andzip.` 前缀的那几棵子树，别的软件加的动词一概不碰。
  - **为已关联的压缩包添加「解压」菜单项** → 写进每个 `Andzip.<id>` ProgID 的
    `shell\extract`（解压）与 `shell\extract-delete`（解压并删除）。这一项存的是**策略**而不是现状快照
    （`context_menu_extract_verbs`，缺省为开）：ProgID 会随新关联不断增多，登记新格式与启动自愈时
    都按它补写一遍，才能保证菜单不会"一半有一半没有"。关掉是真的把键删掉，不是留着改文字。
  - 两个「压缩」开关的状态**读自注册表**：它们是装好就固定的全局动词，被清理软件删掉了界面上
    就该显示没装 —— 凭设置文件回显会让人以为还在。
  - 双击用的 `shell\open\command` 永远不带 `/task=`，因此「解压菜单项」关掉也不影响双击。
    它带 `ProgrammaticAccessOnly`，所以**不进右键菜单**：菜单里那条「用 Andzip 打开」是单独的
    `shell\andzip-open`，命令行写死 `/task=open`。这样"打开"这个名字才真的等于打开 ——
    以前两者是同一条键，于是勾了「双击 = 直接解压」的用户点右键打开得到的是解压。
  - **升级时新增的动词靠 `RepairVerbs` 补齐，退役的靠它清掉**：`IsInstalled` 只看"有没有
    `Andzip.` 开头的键"，所以老用户注册表里只有两条时，第三条永远不会自己出现；反过来
    0.9.12 撤掉的 `compress-7z` 也不会自己消失，所以 `WriteVerbs` 现在先删掉不在本次清单里的
    `Andzip.*` 键再写。一个都没装的范围不动 —— 没勾过的用户不该某天发现菜单里多了东西。
    同理 `WriteCommands` 显式删掉退役的 `shell\auto-extract` / `shell\extract-here` / `shell\extract`(v0.9.5)。

- **压缩页**（`Core/Settings/CompressionDefaults.cs` + `Views/SettingsWindow.cs`）：这一页只决定
  「新建压缩文件」对话框**打开时长什么样**，控件仍可逐次改，所以它不碰注册表、也不影响已经排好
  的任务，落盘就是几行 `settings.ini`。  - **默认压缩级别** —— 5 档（仅存储 / 极速 / 快速 / 标准 / 极限 → 引擎 `-mx=` 0/1/3/5/9）。
    档位按速度排序不是排版习惯：前三档拼速度、标准档看平衡、极限档只看压缩率，
    三套不同的评判标准，所以不能叫"同一算法多跑几遍"。右键「压缩为 ZIP / 7Z」也吃这一档。
  - **不创建根目录 / 排除 Thumbs.db / 排除文件类型 / 压缩后测试 / 完成后不关进度窗口 / 输出目录**，
    六项全部真正生效。
  - 排除模式存**原文**而不是解析好的列表：记录级的相等比较对 `IReadOnlyList<string>` 走引用相等，
    存列表会让"读回来等于写出去"的断言假失败；而且设置页编辑的本来就是那个文本框。
  - 模式分隔符**只认分号**：Windows 文件名里逗号合法（`report,final.txt` 是个真名字），
    按逗号切会把一条模式劈成两条不相干的。
  - 通配语义是朴素的 `*` / `?` 整名匹配，**刻意不**照抄 Win32 的历史怪癖（`*.bak` 会连没有扩展名的
    `BAK` 一起吃掉）—— 那套规则来自 8.3 文件名时代，用户照着 `*.bak; *.tmp;` 写模式时的预期
    就是普通 glob，按 Win32 语义反而会多排除掉他没点名的文件。见 `Core/Archive/FileNamePattern.cs`。
  - **口令与分卷刻意不进这一页**：那两项每次都不一样，记住反而危险 —— 上次压的是加密包，
    这次压的是要发给别人的公开目录，把口令带过去是事故。
  - 「完成后不关闭进度窗口」只作用于这个对话框，**不作用于右键压缩** —— 后者"跑完即消失"
    是更早明确定下的行为，两者不是一回事。
  - 「沿用上次输出目录」的记账项（`compress_last_output_folder`）不在 `CompressionDefaults` 里：
    那是程序自己记的账，用户在页面上看不到，也不该被页面的「立即应用」顺手抹掉。

- **解压页**（`Core/Settings/ExtractionDefaults.cs`）一个下拉 + 三个开关：
  - **双击压缩包文件时** → `打开 Andzip` / `直接解压`（1.6.0 从常规页搬来，键名仍是
    `double_click_action`）。行为由**程序启动时读设置**决定，不是由注册表里哪个动词被调用决定：
    注册表只负责「双击把文件交给我们」，怎么处置那个文件是设置说了算。所以改这一项对已关联的
    所有扩展名立即生效，不需要回头重写注册表。它住在这一页的理由很具体：选「直接解压」时
    走的落点规则就是下面第一条，两个开关是同一件事的两半。
  - **单个文件也放进新建的文件夹** —— 「解压」第一种情形的可选加强。默认关：压一个
    `photo.jpg.gz` 却得到 `photo.jpg\photo.jpg` 不是多数人预期的结果。
    开的时候文件夹名取自**包里那个文件**（去掉扩展名），不是压缩包名 —— 用包名会把 `.gz`
    带进目录名。重名照样走 `名称 (2)` 避让。
  - **解压后打开文件夹** —— 只在真的解完之后打开。失败或取消时打开一个装了一半的目录，
    比不打开更容易让人误以为东西都在里面。
  - **解压完成后不关闭进度窗口** —— 只作用于主窗口的「解压文件」。右键与双击那条路径
    "跑完即消失"是更早明确定下的行为，不跟随这一项，两者不是一回事。
  - `ExtractionLayout.Inspect` 因此从返回枚举改成返回 `ArchiveShape(Kind, RootName)`：
    单文件情形要照文件名建文件夹，就得知道那个文件叫什么。让判定顺手带出来，
    比让调用方回去翻 `listing.Entries[0]` 再假设一次"确实只有一个"要好。
  - 参考软件这一页上的「一次性解压 TGZ/TBZ」「自动检测 Macintosh 代码页」「并行解压」没做：
    前者引擎本来就会展平嵌套归档、不是可关的行为；中者需要引擎侧的代码页猜测；
    后者与压缩共用一个进程级线程数，放这里会让人以为有两个旋钮。

- **查看页**（`Core/Settings/ViewDefaults.cs`）五项，都接得上线：工具栏、状态栏、树形目录、
  默认图标视图、自动展开树（**默认关**，1.3.1 起 —— 深包一打开就摊平的话，第一屏全是文件夹名）。
  - 生效时机分两类，这是界面结构决定的：工具栏是主窗口的一块，设置对话框一关就重新应用；
    树 / 状态栏 / 视图样式属于 `ArchiveView` 的**构造期**决定，所以关掉设置窗口时重画一次当前视图。
    重画要保留用户原来停在哪一面 —— 正看着首页的人不该被扔进压缩包视图。
  - **"重新应用"之前必须先 `_settings.Reload(DefaultFilePath)`**：设置窗口写盘用的是它自己
    `Load` 出来的那份实例，主窗口手里那份是启动时的快照。不重读，用户点完「立即应用」界面不动，
    而且主窗口下一次写盘会拿旧快照把整个文件盖掉，那一项设置连重启都找不回来
    （第七节第 26 条，1.3.0 的「设置不生效」就是这么来的）。
  - 关掉树不能只把面板 `IsVisible = false`：`Grid` 仍会按 `300,4,*` 留下两列空白，
    变成一条拖不动也点不到的死区。要把列宽一起归零。
  - 参考软件这一页上的「列设置」「图像预览」「压缩文件注释」「置顶」「颜色设置」「视图样式子菜单」
    没做 —— 前四个对应的功能本身还不存在。
- **语言页**（`SettingKeys.Language`）：候选来自 `LangCatalog.Languages`，也就是
  **实际加载到的那些包**，显示名用各包自己的 `LANG_NAME`。所以往程序目录 `langs/` 里放一份
  新语言，这一页会多一项而且选了真能切；反过来，写死两个名字就会出现"列表里有、切过去又回退"。
  - `App` 因此改成**先读设置、再建语言包** —— 顺序反了这一项就永远慢一拍，
    而"改了语言要重启才对"看起来像是功能坏了。
  - 换语言当场只翻 `LangCatalog`：之后新建的对话框与压缩包视图是新语言，已经画好的菜单、
    工具栏、标题是构造时取一次就固化到控件上的，要重启。页面上如实写明，
    不做"看起来全变了"的假动作。
  - 设置里存的代码在当前机器上不存在（换机器、删了 `langs/`）时，下拉框停在列表第一项，
    而不是留一个空白框让人以为没读到。

- **高级页**三项：标题栏显示完整路径、临时文件夹、导出设置。
  - 三处 `Title = …` 收成一个 `ArchiveTitle(path)` 方法。分开写迟早分叉 ——
    切视图时标题突然变样就是这么来的。
  - 临时目录只服务一处：拼接 WinZip 风格分卷（`name.z01 + name.zip`）时的落地文件。
    7z 风格的分卷由引擎自己取兄弟卷，不经过磁盘。指定目录不可用时**退回系统临时目录而不是抛异常**：
    分卷包打不开，跟临时目录设在哪儿比起来是重要得多的事。
  - 「导出设置…」的可用状态跟着 `settings.ini` 在不在走 —— 首次运行还没写过设置时是灰的，
    而不是点下去报一个"文件不存在"。
  - 参考软件这一页上的其余项都没做，理由逐条写在第六节第 20 条；共同点是它们要么依赖还不存在的
    功能，要么是引擎侧策略，要么描述的正是现在的行为（做成开关等于凭空造两个没人会关的选项）。
- **安全页**：会话内口令记忆。
  - 打开一个加密包时输过一次，解压它就不再问。清单里那个口令不对（包换过口令）时
    **先忘掉再问**，不会拿同一个错口令撞第二遍。
  - 关掉这一项会**连带清掉已经记住的** —— 只停"新增"而留着旧数据，用户以为没了、其实还在内存里。
  - 口令<strong>只在内存</strong>：不写 `settings.ini`，不写注册表。页面上直接写明这一点，
    并说明参考软件那个跨重启的「口令管理器」为什么没做 —— 要做对得用操作系统级凭据保护
    （Windows 上是 DPAPI），那需要一个 Windows 专用的依赖，而本项目还要在 Linux 上构建；
    把口令明文写进设置文件不是它的简化版，是一个谁都会踩的坑。
  - 进程级会话状态放在 `App/Session.cs` 而不是挂 `App` 类上：在 `namespace Andzip.App` 内部写
    `App.Passwords` 时，编译器会先把 `App` 解析成命名空间本身。一个不会撞车的容器名比跟解析
    规则较劲省事。

### 界面风格与设计令牌（FR-1～FR-5 的视觉层，1.4.0）

规范全文在 `docs/界面设计规范.md`；这里只记**为什么这么定**与**踩到的三件事**。

- **三个新文件**：`Design.cs`（颜色 / 圆角 / 间距 / 字号 / 图标尺寸令牌）、`Chrome.cs`（交互态）、
  `Icons.cs`（图标几何）。分工是"数值 / 状态 / 形状"，界面代码只引用它们。
  以前 23 个字面色值散在 10 个文件里，改一次配色要全仓搜替换 —— 那才是这次真正的债。
- **`Design` 不叫 `Theme`**：Avalonia 的 `Control` 上有一个 `Theme` 属性（`ControlTheme`），
  在窗口类里写 `Theme.Surface` 会被解析成"这个控件的 ControlTheme 的 Surface"，
  报的是 `“ControlTheme”未包含“Surface”的定义`。名字撞了不是风格问题，是编译不过。
- **悬停态为什么不能用样式写**：`Application.Styles` 里加
  `Style(x => x.OfType<Button>().Class(":pointerover"))` 之后，把真指针移上去，
  **中心像素一个字节都没变** —— 主题内部的 `ControlTheme` 优先级更高。
  所以 `Chrome.cs` 直接接 `PointerEntered/Exited/Pressed/Released`。
  副作用是好事：这套状态**能被测试证明存在**（headless 的 `MouseMove` 会真的触发这两个事件），
  于是有了 `DesignTokenTests.ToolBarButtonsShowAHoverState` 这种"量一个点变没变"的断言。
- **圆角不是愿望**：先量过 SimpleTheme 吃不吃 `CornerRadius`（`Button` / `TextBox` / `ComboBox` 都吃），
  才敢把它写进规范。对照组（不设圆角的同一个按钮）也在断言里 —— 不然"四角是白的"
  可能只是因为量错了位置。
- **两处刻意保持方角**：列分隔条、树/列表的选中高亮条。它们贴边，圆了会在角上露出底色缝。
- **窗口底色从品牌蓝改成白**：以前整窗是 `#208CFB`，蓝色从工具栏缝隙漏出来，
  内容区一有留白就变成"蓝底上贴了张表"。现在蓝只待在工具栏那一条里，
  层级靠底色差（`Surface.Base` / `Muted` / `Sunken`）+ 1px 线表达 —— SimpleTheme 用不了阴影。
- **设置页左侧导航从实心蓝条改成浅灰 + 选中淡蓝 + 3px 标记条**：蓝色该留给"动作"，
  导航是"位置"，整条实心蓝会把位置读成可点的主命令。
- **规范里主动砍掉一条**：列表斑马纹。做是能做，但 28px 行高下浅条纹只给长表加噪声，
  而选中态本来就盖在条纹上。文档里写明"不做以及为什么"，比留一条没人实现的规则好。

### 夜间模式（1.5.0）

规范在 `docs/界面设计规范.md` §十；这里记的是**为什么这么实现**与**没做到的部分**。

- **深浅全靠自己的调色板，别指望主题**：探过 `SimpleTheme` —— 它暴露 55 个资源键，
  里面**没有表面色**；把 `RequestedThemeVariant` 设成 `Dark`，窗口角仍是 `#FFFFFF`，
  整幅画面的暗像素占比只从 0.3% 变到 3.9%。所以 1.4.0 那次"把 23 处字面色值收进 `Design.cs`"
  是这次能做深色模式的前提 —— 否则要翻的是散在十几个文件里的颜色。
- **两套调色板不是取反，是重算角色**：工具栏那条蓝在深色下要**压深**（它是白字的底，
  提亮会把对比度打到 AA 以下），而选中行/信息条那类蓝要压成深蓝（它们是浅字的底）；
  分隔线方向要翻转；语义色换成粉彩版本；底不用纯黑（光晕）。
- **对比度是算出来的**：`PaletteContrastTests` 按 WCAG 2.1 公式实算两套 × 9 个配对，
  规范表里那些数字就是它报的。文档里写"5.6:1"这种数，不写测试就会在下次改配色时变成假话。
  顺带有反面断言"深色那份不能其实是浅色"—— 否则配对断言全过而深浅根本没区别。
- **切换必须重建而不是改属性**：没有 XAML、没有资源绑定，颜色在构造时就固化到控件实例上了。
  所以 `MainWindow.ApplyTheme()` 改外壳那几处底色 + 整份重做内容区，并保住"用户正看着包"这个位置。
  `Design.Use()` 在没变化时不触发事件，否则设置页每刷新一次界面闪一下。
- **测试要串行**：调色板是进程级全局，一个用例切深色、另一个正在断言浅色像素会互相踩。
  第一反应是加 `[assembly: CollectionBehavior(DisableTestParallelization = true)]` ——
  **那会把 Avalonia 的测试 fixture 弄坏**，所有渲染用例报 `Unable to locate IPlatformRenderInterface`
  / "没有画面"。改成给相关类挂同一个 `[Collection("界面状态")]`，只串行这一组，其余照旧。
- **帧缓冲的通道序**：headless 这个后端给的是 R,G,B 顺序而不是文档默认的 Bgra32，
  按 Bgra 读会把 `#1F2328` 读成 `#28231F` —— 断言"颜色对不对"时全是假阴性。
  现在 `Pixels.At` 按实测顺序取，比较仍走"通道排序"兜底。
- **没做到的**：标题栏（DWM 属性返回 `S_OK` 但颜色不变，见第七节第 28 条）、
  SimpleTheme 自己画的勾选框/下拉弹出/提示气泡/滚动条/菜单弹出层（清单在规范 §10.4）、
  以及"运行中跟随系统切换"（没验证，最坏是重启才跟上）。

### 其它

- 语言包、主菜单模型、快捷键、版本号读取：原样保留，测试全绿。
- `ArchiveEngine`（新增）：界面可查询引擎是否可用、版本、格式/编解码器数量，并设置线程数
  与内存上限。「线程数」下拉框从此真正生效（原先是禁用占位）。

## 六、未完成 / 已知限制

**读之前请先确认你要做的功能不在这里。**

### 压缩内核侧

1. **ZIP 的密码只支持 ASCII**。7-Zip 的 zip 写入端显式检查
   （`ZipHandlerOut.cpp` 的 `IsSimpleAsciiString`），非 ASCII 直接 `E_INVALIDARG`，
   ZipCrypto 与 AES 都拦。Core 已提前翻译成可本地化的
   `ArchiveConstraintException(NonAsciiPasswordNotSupported)` 并提示改用 7Z。
   **7z 的中文密码完全正常**（已实测往返）。
   → 这是相对旧 SharpZipLib 实现的**功能回退**，旧实现可以写中文密码的 zip。
2. **条目「文件说明」不支持**。7-Zip 的 out-handler 属性表里没有归档注释项，逐条目注释
   只在 ZIP 上有一条按字节截断的窄路径。现在写这类包会成功，但 `Warnings` 里会明确说
   「entry comments are not supported」，不会静默吞掉用户输入。
3. **分卷输出只有 ZIP**，且是 Core 把完整归档切成块 —— 不是引擎的卷机制。7z/xz 的原生
   分卷（`archive.7z.001`）写入未实现：直接驱动 `CMultiOutStream` 曾出现「报告成功但
   一个文件都不生成」的丢数据故障，因此内核层现在对 `volume_size` 一律返回
   `AZ_ERROR_UNSUPPORTED`。**读取**分卷是好的。
4. **不能往已有归档追加、删除成员或原地更新**。引擎的 `UpdateItems` 能做，但那要先读出
   旧归档再重放成员，尚未实现。
5. **`-mx=0`（仅存储）对 gzip/bzip2/xz 不改变体积**：这些单流格式的编码器各级别都走
   同一套压缩，tar 层本来就不压缩。所以 TGZ 的「仅存储」只是被接受，不会让包变大。
6. **7-Zip 能容忍被截断的中央目录**：截掉尾部（含 EOCD）的 zip 可能仍然打开成功。数据
   本身被破坏时 CRC 会发现。测试里已把这个行为钉住，避免将来被误判为回归。
7. **额外编码器（zstd / lz4 / brotli / lizard 的编码）需 `-ExtraCodecs`**，本次未开启验证。
   Zstandard 的**解码**可用。

### 界面与业务侧

8. **压缩包视图只到「浏览」**：右键菜单、列设置（显隐与列宽记忆）、双击文件打开
   （解压到临时目录再交给系统关联程序）、拖拽解压、图像预览面板都没有；工具栏的
   「添加 / 删除 / 测试 / 扫描」与语言按钮仍是禁用占位。
9. **没有「添加到已有压缩包」「测试并修复」「生成 SFX」**。
10. **符号链接与 POSIX 权限**：界面里的「存储符号链接」复选框仍是禁用占位；引擎侧
    `posix_mode` 有通道但界面没接。
11. **进度按条目/字节上报，但逐条解压路径下没有单条目内部的字节进度**（外壳的
    `ReadEntry` 不接回调）。
12. **解压口令仍是「先探测再一次性输入」**，没有用引擎的口令回调做「解压中途要口令」。
13. **`VersionInfo` 与 `ArchiveTester` 门面尚未被界面调用**（`VersionInfo` 只有测试在用）。
14. **语言包本轮新增 21 个键**（工具栏文案、压缩包视图列名与附加信息），同时删掉不再使用的
    `TEXT_HELP_PAGE` / `TEXT_STARTUP_OPEN` / `TEXT_STARTUP_NEW` / `TEXT_ALL_FILES`；
    其它语言的包（如 Bandizip 自带的 Russian）未同步。
15. **异常文本仍是英文**：内核回传的消息直接进错误框，只有少数约束类错误走了本地化文案。
19. **通过关联拉起时，会把 `Andzip.*` ProgID 的命令行校正到当前运行的这个 exe**（`App.RepairStaleRegistrations`）。
    这是有意的：绿色版文件名带版本号，升级后注册表还指着上一个 exe，而老二进制不认新行为，表现成
    「设置改了没用」。代价是同一台机器上跑多份 Andzip 时，**最后一次被双击拉起来的那份会占用关联**。
    不想被改就用「文件关联」页重新应用一次，或别在已关联的机器上临时运行第二份。
20. **设置窗口九个页面已全部实装**（常规 / 文件关联 / 上下文菜单 / 压缩 / 解压 / 查看 / 安全 / 高级 / 语言），
    没有占位页了。每一页只放真正接得上线的开关。
    参考软件常规页上的「始终在添加/删除/重命名文件时检查文件」「贴靠窗口」
    「显示网格线」「整行选择」「单击打开项目」与「更新设置」下拉都没有做 —— 前五个属于列表控件的
    行为改造，后者需要真实的更新通道，都不适合做成一个不生效的勾选框。
    参考软件关联页上的「基本选项」按钮没有跟着做 —— 它的行为无法从截图确定，放一个不知道会不会有用
    的按钮不如先不放。
21. **被 `UserChoice` 保护的扩展名设不了默认**：Windows 10 1709 之后默认应用有哈希保护，
    伪造那个哈希属于绕过系统安全机制，不做。这类扩展名在关联页列成红条并给「设为默认…」按钮，
    直接跳到系统设置里对应那一项（本机实测 `.7z` 就属于这种：ProgID 与 `Software\Classes` 都写对了，
    但 `UserChoice` 还写着 `Bandizip.7z`，双击仍然是 Bandizip）。
    「打开方式」列表是共享的，取消勾选只删我们自己挂的 `Andzip.*` 值，不碰别的软件留的。
22. **右键菜单是静态注册表动词，不是 COM shell 扩展**，因此有三条跟着来的限制：
    - **Windows 11 上落在「显示更多选项」二级菜单里**，不是新菜单第一层。进第一层必须实现
      `IExplorerCommand` 的 in-proc 扩展 —— 额外的原生 DLL、注册步骤，而且它崩了会把资源管理器
      一起带崩，本版不做。
    - **一次只处理一个文件或一个文件夹**：静态动词只能用 `%1`，多选的可信列表要靠 `%V`/`%L`
      并且行为在不同版本上不一致。多选请进主窗口用「新建压缩文件」。
    - **菜单文字是死的**：注册表动词没法把 `%1` 的实际名字渲染进标题，所以写的是「压缩为 ZIP」
      而不是参考软件那种「压缩为 "文件名.zip"」。
23. **右键「压缩为 ZIP / 7Z」走固定默认档位**：正常压缩、无口令、不分卷、不测试、压完不删源。
    需要口令 / 分卷 / 极限压缩 / 压缩后删除原始文件的，用同一个菜单里的第三条
    「压缩到…（可设密码 / 分卷）」—— 它把「新建压缩文件」对话框开起来，输入与包名已经预填好。

24. **夜间模式只覆盖我们自己的表面**：SimpleTheme 没有深色表面色（55 个资源键里就没有，
    `ThemeVariant.Dark` 下窗口角仍是 `#FFFFFF`），所以以下几处在深色下仍偏浅 ——
    勾选框/单选钮的方框内部、下拉弹出项背景、提示气泡、滚动条槽、菜单弹出层。
    清掉它们要给这 5 类控件各写一份 `ControlTheme`，收益是几像素，先不做（清单见规范 §10.4）。
    **标题栏也翻不深**：`DwmSetWindowAttribute` 返回 `S_OK` 但本机颜色不变，
    代码留着（Win11 上大概率有效），文档不承诺（第七节第 28 条）。
    「跟随系统」在运行中能不能跟上系统切换，未验证 —— 最坏是重启才生效。

### 平台

16. **Linux / macOS 的运行时在本机验证不了**。这台机器没有 WSL 也没有 Docker，跑不了 Linux
    二进制；macOS 连编译都没做过。CI 里已经挂了 `linux` / `macos` 两个作业去真机执行
    `andzip_core_tests`，但**在仓库推上远端之前它们一次都没跑过**，所以这条只能算「有手段了」
    而不是「验证过了」。顺带说清一个已经修掉的事实：在改名之前，即使跑起来，.NET 侧也永远
    加载不到内核（产物叫 `andzip_core.so`，外壳探测的是 `libandzip_core.so`），
    见第七节第 13 条。
17. **Windows arm64 只配置未构建**。
18. **静态库消费方必须整体链入**：注册 handler 的目标文件不被任何符号引用，普通静态链接
    会丢掉它们，结果是「库能加载、格式表是空的」。CMake 目标已用 `/WHOLEARCHIVE` 处理；

    `-Wl,--whole-archive libandzip_core.a -Wl,--no-whole-archive`。

## 七、重构过程中遇到的问题（以及怎么定位的）

记录过程而不只是结论，因为多数坑的「症状」和「原因」隔了好几层。

### 1. ZIP 里的中文文件名被其它工具读成乱码

**症状**：我们自己的界面、命令行工具、甚至 GNU 工具链都正常，但用 BCL
`System.IO.Compression` 和 SharpZipLib 打开我们写的 zip，`中文名字.txt` 变成乱码。

**定位**：写了一个诊断测试，把同一个包分别用三种实现读一遍，发现文件里存的**字节其实是
正确的 UTF-8**，但 zip 的「语言编码标志位」（通用标记位 bit 11）没有置上，于是别的实现按
OEM 代码页（这里是 GBK）解 UTF-8 字节。

**原因**：7-Zip 的 zip 写入端默认用 `CP_OEMCP` 转名字，且只有显式要求时才走 UTF-8 并置标志位。

**修复**：内核的 `BuildProperties` 对 zip 下发 `cp=65001`（并附 `cu=on` 表达意图）。
注意 `cu=on` 单独用在这个版本里**不生效**，`cp` 才是决定性的；而 `cp` 必须传数值，
传字符串会被判 `E_INVALIDARG`。

### 2. 往 tar 里加一个目录，整个写入失败

**症状**：`az_writer_finish` 返回 `ErrorInvalidArg (Win32 87)`，但同样的目录压成 zip/7z 正常。

**定位**：用命令行工具单独压 tar 复现，再读 7-Zip 的 `TarHandlerOut.cpp`：它在
`newData=1` 时要求 `kpidSize` 必须是 `VT_UI8`，而我们的回调对目录返回 `VT_EMPTY`。
zip / 7z 不较真，tar 较真。

**踩过的弯路**：先改成「目录报 `newData=0`」，结果原生测试**直接进程崩溃** —— 因为
`newData=0` 会让 handler 去 `indexInArchive` 里取数据，而我们所有条目的该值都是
「不在归档中」。

**正确修复**：`kpidSize` 一律返回 `VT_UI8`，目录返回 0。

### 3. 归档注释把整次写入带崩

`az_create_options.comment` 原先被映射成属性 `"c"`，但 7-Zip 的 zip 与 7z out-handler
属性表里都没有 `"c"`，未知属性直接 `E_INVALIDARG`。改成不下发、只回一条「被忽略」的警告。

### 4. `-mx=0` 与 `m=Deflate` 互相覆盖

**症状**：选「仅存储」压 200 KB 文本，产物 397 字节 —— 和「正常压缩」一模一样。

**定位**：分别用外壳（只给 Level=0）和 Core（Level=0 + 默认方法 Deflate）压同一个文件，
外壳得到 200,148 字节、Core 得到 397 字节，说明是**同时下发方法名和级别 0** 时，
7-Zip 按 Deflate 的默认级别压了，把「不压缩」吃掉了。

**修复**：级别为 0 且用户没显式选方法时，推断成 `Copy` —— 但**只有该方法在该格式的方法表里
存在时才推断**：tar 没有压缩方法属性，给它下发 `m=Copy` 会重新触发问题 2 那类
`E_INVALIDARG`。

### 5. 分卷：切块函数把刚写好的归档删了

`SplitVolumeSupport.Split(source, archive, …)` 会先删 `archive` 再切。我最初把同一个路径
同时当 source 和 archive 传入，于是 `FileNotFoundException`。修复是复合格式与分卷都先写到
中间文件，切完/压完再删中间文件；中间文件用 `<stem>.tar` 这类有意义的名字，因为它会成为
外层归档的成员名。

### 6. 单文件绿色版找不到压缩内核

`dotnet build` 和**非**单文件的 `dotnet publish` 都正常，只有单文件包运行时报
"compression engine unavailable"。原因：`andzip_core.dll` 是以 `None + CopyToOutputDirectory`
的形式进入输出的，属于「内容」而不是 RID 资产，`IncludeNativeLibrariesForSelfExtract`
只管后者。改用 `IncludeAllContentForSelfExtract=true`，并在 `build.ps1` 里加了发布后扫描
产物字节的断言。

### 7. 测试主机中途崩溃，用例数从 178 掉到 97

一次全量运行里报告数骤降。逐个筛除后发现是**问题 2 的中间修复**（`newData=0`）导致的原生
崩溃，不是测试框架问题。教训：用例总数突然变化本身就是信号，不能只看「失败 1」。

### 8. 若干「测试断言的是旧实现的细节」

这类不是 bug，但必须逐条判断「行为变了」还是「实现变了」：

- 压缩级别记录里带着 `System.IO.Compression.CompressionLevel` —— 是泄漏到接口上的类型，删掉。
- 条目方法用 ZIP 规范编号 + `-1` 占位 —— 换成引擎方法名。
- 「可创建格式只有 ZIP/TAR/TGZ/GZ」—— 这正是本次要改的东西，改成钉住「7Z/BZ2/XZ 现在可写」。
- 「zip 默认方法必须是 Deflate」—— 7-Zip 对压不动的数据会自动退回 Store，这是正确行为，
  于是把测试数据换成可压缩内容，并补一个测试专门钉住这个回退。

### 9. 外壳的选项块被提前释放（use-after-free）

`ArchiveWriter.Create` / `ArchiveReader.Open` 原本写成 `using var args = NativeArgs.Create(options)`，
方法一返回就把 `az_create_options` 连同里面的 `az_callbacks`（进度回调函数指针 + ctx）释放了，
而内核是在之后的 `Finish()` / `ExtractTo()` / `Test()` 里才回调它。改成把 args 的**所有权交给返回的
句柄对象**：`_ownedArgs` 字段，`Dispose()` 里先 `az_writer_free` / `az_archive_close`，再释放 args；
构造失败的路径用 `catch { args?.Dispose(); throw; }` 兜住。

这个改动是对的，但它**没有**让崩溃消失 —— 说明还有第二个原因。

### 10. 间歇性 0xC0000005：内核里未初始化的 `PROPVARIANT`

现象：`dotnet test` 每隔几次就报「测试主机进程崩溃」，用例数从 178 掉到 169/172/164……
栈顶固定在 `az_writer_finish`。定位过程（值得照着复用）：

1. **缩小到单个测试类**：只跑 `ZipEncryptionTests`（同一个集合，串行）仍然崩 —— 排除并行竞争。
2. **写不依赖 C# 的最小复现**：C 语言直调 ABI，把「建包→加成员→finish→释放」循环 20,000 次，
   动态 `LoadLibrary` 加载、每次成功后调 `az_last_error_message()`，仍然一次都不崩。
   结论：需要 CLR 宿主才会崩，问题在“两边都会走、但内存状态不同”的地方。
3. **按维度二分**：`mt` / `solid` / 有没有进度回调 / 有没有密码 全部无关；
   **格式是 zip 就崩，7z 基本不崩**。
4. **看崩溃地址**：用 `DOTNET_DbgEnableMiniDump` 收全量转储，`dotnet-dump` 取寄存器与模块表。
   转储里的 RIP 已经是 createdump 自己的等待调用（拿不到出错现场），本机又不是管理员，
   WER LocalDumps 与 PageHeap 都用不了 —— 于是改用**进程内自检**：
5. **在宿主里校验堆**：P/Invoke `ucrtbase!_get_heap_handle` + `kernel32!HeapValidate`，
   每次操作后校验 CRT 堆与进程默认堆。堆看起来是好的，说明破坏发生在“还没写坏链表的
   那一步”—— 也就是野指针释放，而不是越界写。
6. **回到代码里找「对未初始化内存做释放」的形状**：`native/src/api` 里有一处惯用写法
   （8 个局部变量 + 3 个属性辅助函数 + `PropEntry::Value`）：

   ```cpp
   PROPVARIANT prop;
   ::PropVariantClear(&prop);   // ← 读的是没初始化的 prop.vt
   ```

   `PropVariantClear` 会**按 `vt` 分派释放**：`vt` 恰好落在 `VT_BSTR`/`VT_LPWSTR`/`VT_UNKNOWN`
   这些分支时，它会对一个垃圾指针执行 `SysFreeString`/`CoTaskMemFree`/`Release`。
   这就是全部现象的解释：`CObjectVector::AddNew()` 用的是 `new T`（默认初始化，POD 成员
   **不清零**），而栈上的局部变量同理。纯 C 程序里这些内存大多是新页的 0（`vt==VT_EMPTY`
   → 无害），CLR 进程里同一个堆/同一批栈页塞满了托管帧与 LocalAlloc 残留，`vt` 经常是垃圾值
   → 千次左右踩中一次。ZIP 分支每次写入要设 6～10 个属性，所以明显比 7z 容易崩。

   修法：把“先 Clear 再用”换成“**先 Init 再用**”。局部变量改成
   `::PropVariantInit(&prop)`（只写 `vt = VT_EMPTY`，不读任何字段），`PropEntry` 补默认构造函数
   `PropEntry() { ::PropVariantInit(&Value); }`，三个 `Add*Prop` 辅助函数里的 Clear 全部换成 Init；
   后续复用变量时的 Clear 保留（此时 `vt` 已经是合法的）。POSIX 侧在 `az_pch.h` 补了
   `PropVariantInit` 的内联垫片，Linux x86_64 / aarch64 交叉编译已验证通过。

   验证：改前 1500 次的组合 5 组里崩 3～4 组；改后同一批配置 5 × 6 × 1500 = 45,000 次，加上
   常驻检查的 6 × 4000 = 24,000 次，合计 **69,000 次往返 0 崩溃**，
   `dotnet test Andzip.slnx` 连续 5 次稳定 178/178。这一类缺陷已经固化成一条常驻检查
   （`Andzip.Native.Tests` 的 `writer stress`，4000 次写入），做法与反向验证见第九节。

   两条可沉淀的经验：①「纯 C 复现不了」不等于「不是内核的 bug」，堆的**内容**才是变量；
   ② 没有调试器权限时，`_get_heap_handle`/`HeapValidate` + 逐调用自检 + 代码里搜
   “对未初始化结构调释放函数”这个模式，比死磕栈回溯更快。

   附带修掉一个长期存在的 `C4819`：`az_writer.cpp` 里有两段中文注释，而内核工程没有加
   `/utf-8`，编译器按本地代码页（936）读源码会报警。既然 `native/` 的注释约定是英文，
   就把那两段翻译成英文（内容一字不差地保留），整个 `native/src`、`native/include` 现在
   是纯 ASCII，构建 0 警告。

### 11. `Andzip.Native.Tests` 不在 `dotnet test` 的射程里

它是**不带 xUnit 的控制台自检程序**（`OutputType=Exe`，69 条断言）。`dotnet test` 对它只能
“还原，然后什么都不做”，所以「测试全绿」曾经只覆盖了 Core 的 178 个用例。现在
`build.ps1` 会显式把它跑一遍并把非零退出当失败。

### 12. 双击 `Andzip.slnx` 后 F5 报「无法直接启动带有『类库输出类型』的项目」

第一反应是「`.slnx` 记录不了启动项目，所以只能让用户自己右键设为启动项目」—— **这个结论是错的**，
它把可以修的东西推给了用户。真正的机制看 VS 工具栏就知道：启动项目下拉里是 **`Andzip.Native`**，
一个类库。为什么会是它？

对比两个解决方案就清楚了：

| 解决方案 | 工程路径排序后的第一项 | VS 默认启动项目 | F5 |
|---|---|---|---|
| 根目录旧 `Andzip.slnx`（只有 `src/...`、`tests/...`） | `src/Andzip.App/Andzip.App.csproj` | Andzip.App | ✅ |
| 重构后的 `Andzip.slnx`（外壳在 `native/csharp/...`） | `native/csharp/Andzip.Native/...` | **Andzip.Native（类库）** | ❌ |

**VS 在没有 `.suo` 状态时按项目路径的字典序选默认启动项目**，而不是按 `.slnx` 里的声明顺序 ——
否则 `Andzip.App` 明明是文件里第一行，不该被跳过。`n` < `s`，所以 `native/csharp/Andzip.Native`
插到了队首，把启动项目占成了类库。

修法不是去教用户点右键，而是**让字典序第一项必须是主程序**：把两个 C# 外壳工程
`Andzip.Native`、`Andzip.Native.Tests` 从 `native/csharp/` 移到 `src/` 下，和其它 C# 工程放一起。
移动后要改的引用一共 6 处：`Andzip.slnx`、`Andzip.Core.csproj` 的 `ProjectReference`、
`build.ps1`、`run.ps1`（两处）、`native/scripts/build-windows.ps1` 的 DLL 暂存路径 —— 外壳自己的
`ProjectReference` 是相对路径，跟着一起移动后仍然正确。另外必须删掉目录里的 `.vs/`，
它里面那份 `.suo` 还记着 `Andzip.Native`，不删的话修好了规则也照样报错。

顺带说明：`native/` 仍然是完整的 C/C++ 内核（`include/`、`src/`、`cmake/`、`scripts/`、
`third_party/`、`tools/`、`tests/native`），只是不再夹带 .NET 工程；外壳是内核 ABI 的
**消费者**，和其它 C# 工程同层，这个归属本来就更合理。

验证：复制一份只留 `Andzip/` 的干净目录（34 MB，无任何构建产物）→ `dotnet build`、
`dotnet test`（178）、外壳自检（69）、`build.ps1` 打包、`run.ps1` 启动 —— 全部通过；
`Andzip.slnx` 里字典序第一项现在是 `src/Andzip.App/Andzip.App.csproj`。

### 13. Linux / macOS 上内核**永远加载不到**：产物文件名与外壳探测名不一致

写 CI 的 Linux 作业时顺手发现的。它一直藏在「本机跑不了 Linux 二进制」这句话后面。

- `native/CMakeLists.txt` 里的 `PREFIX ""` 是**无条件**设的，于是 Linux 产物叫
  `andzip_core.so`；
- 外壳 `NativeLibraryResolver.FileName` 在非 Windows 上探测的却是
  **`libandzip_core.so`** / `libandzip_core.dylib`；
- `build-unix.sh` 自己也按 `libandzip_core.so` 去找（用来打印内核版本），所以那段
  `azcore version` 在 Linux 上从来没执行过 —— 被 `[[ -f ]]` 静默跳过了。

三处两两不一致，后果是：**在 Linux / macOS 上 .NET 侧永远找不到引擎**，程序只会显示
「compression engine unavailable」。Windows 看不出任何问题，因为 MSVC 本来就不加前缀。
之前所有交叉编译验证都只做到「`.so` 编得出来、导出符号对」，从没检查它**叫什么名字** ——
这正是「只编译不执行」的代价，也是加 CI 的意义。

修法：`PREFIX ""` 只在 `WIN32` 下设置，其它平台保留 CMake 默认的 `lib` 前缀，三处对齐到
`libandzip_core.so` / `libandzip_core.dylib`。改完重新交叉编译三个目标验证：
`build/linux-x64/bin/libandzip_core.so` 与 `build/linux-arm64/bin/libandzip_core.so` 各 41 个
导出，静态库 `libandzip_core.a`（30.9 MB）被 `azcore` 成功链接。

### 14. 门禁脚本自己会「吞掉失败」并报告全绿

`verify-all-targets.ps1` 的每一步只检查 `$LASTEXITCODE`。但**可执行文件找不到**时抛的是
`CommandNotFoundException`，`$LASTEXITCODE` 根本不更新（还是 0）—— 于是这台机器上 `cmake`
不在 PATH（它装在 VS 里面）的情况下，Linux 三个目标整段没跑，脚本却以退出码 0 结束。
我第一版 README 里「一条命令跑完所有平台」那句话，就是被这个假绿骗出来的。

两处修：① `Invoke-NativeStep` / `Invoke-Gate` 一律 `try { 步骤 } catch { 带标签重新抛出 }`，
外部命令的非零退出与终止错误都算失败；② 脚本自己用 vswhere 定位 VS 自带的 CMake/Ninja 并加进
`PATH`，找不到就明确报错，而不是假装跑过。修完 Linux 三个目标才第一次真正跑通（见第 13 条）。

同类问题还有一处，是 `ci.ps1` 自己的：`& build-windows.ps1` 是**同进程**调用，它导入的 vcvars
环境会漏进 `ci.ps1`，其中 `Platform=X64` 被 MSBuild 当成解决方案平台，于是后面的
`dotnet build` 报 `MSB4126: The specified solution configuration "Release|x64" is invalid`。
改成用子进程跑引擎脚本，并在开头清掉继承来的 `Platform`（解决方案只有 Any CPU）。
这个坑是**本地跑第一次 `ci.ps1` 时暴露的**，不是靠读代码读出来的 —— 门禁脚本本身也需要门禁。

### 15. 「已经关联了，双击却不是我们」：`UserChoice` 盖在 `Software\Classes` 上面

用户报的是 `.7z` —— 关联列表里勾着，右键「打开方式」也有 Andzip，双击却照样开出 Bandizip。
把三条键并排 dump 出来才看清问题不在我们这一侧：

| 键 | `.7z` | `.zip` | `.rar` |
|---|---|---|---|
| `HKCU\Software\Classes\<ext>` 默认值 | `Andzip.7z` | `Andzip.zip` | `Andzip.rar` |
| `…\Explorer\FileExts\<ext>\UserChoice\ProgId` | **`Bandizip.7z`** | `Andzip.zip` | （无此键） |
| `HKCU\Software\Classes\Andzip.<id>\shell\open\command` | 正常 | 正常 | 正常 |

也就是说 ProgID 三件套全对、扩展名默认值也写进去了，唯独 `UserChoice` 还留着上一个软件，
而 **Windows 查默认程序时先看 `UserChoice`**。`.zip` 恰好被显式选过一次所以正常，
`.rar` 从没被选过所以没有这个键 —— 三个格式三种状态，才显得像"只有 7z 有 bug"。

`UserChoice` 里还有一个 `Hash`，是 Windows 10 1709 起用**每用户随机密钥**算的，
专门防第三方程序静默抢默认应用。伪造它就是把系统安全机制绕过，而且随版本更新随时失效，
**不做**。合法出路只有两条：让用户在系统设置里选一次，或者用 `SHOpenWithDialog` 让用户点「始终」。
这里选前者（`ms-settings:defaultapps?fileExtension=.7z`），因为它不弹我们自己的模态框、
行为在各版本上一致，而且用户本来就该看到是自己改的。

界面侧的教训更值得记：**「已关联」和「双击走我们」是两个状态，界面上必须分开表达**。
以前关联页只回显注册表里的登记结果，被 `UserChoice` 挡住时那个勾依然是亮着的 ——
用户看不出任何异常，只会得出"这软件做不了关联"的结论。现在 `ShadowedDefaults()` 会把它
单列成一条红字并配「设为默认…」按钮，登记过程中新挡下的更是当场跳过去。

### 16. 「登记 ≠ 能写」：五个额外编码器进不了 7z 的写入路径

`-ExtraCodecs` 构建里 `azcore codecs` 明确报告 ZSTD / LZ4 / LZ5 / LIZARD / BROTLI 的
`ENC = yes`，537 项原生检查全过 —— 但 `azcore create x.7z -m LZ4` 一律
`E_INVALIDARG (Win32 87)`。标准方法（LZMA / LZMA2 / PPMD / BZip2 / Deflate / Deflate64）全部正常。

失败集合正好等于**没出现在 `7zHandlerOut.cpp:148` 那个 `switch (methodFull.Id)` 里的方法**；
而同样不在那里的 `-mm=Copy` 更狠，不返回错误，直接段错误。所以"编码器登记成功"这件事
**不能当成"这个方法可用"的证据** —— 界面上一个都没列。

插桩为什么没查出来，也值得记一笔：DLL 里 `fprintf(stderr, ...)` 在这个控制台完全看不见
（stdout 正常），改成 `fopen` 写文件也没有产出。也就是说**下一次要换通道** —— 写进原生测试套件，
它在同进程里、往 stdout 打印，通道是通的。

### 17. 测「检测类功能」之前，先确认你改的那个字节真的会被检测

同一轮里犯了两次同构的错，都是**测试自己骗自己**：

- 完整性检测：第一版探针拿 4000 个 `a` 造包，翻掉"文件正中间"的字节。可那种包压完只剩几十十字节，
  正中间落在**中央目录**而不是数据区 —— 测试照样通过，于是差点得出"引擎根本没校验 CRC"的结论。
  换成压不动的随机语料后，真实行为才浮出来：引擎逐成员校验，失败消息点名成员。
- ZIP 修复：第一版"抹掉中央目录"用的是**猜的范围**，结果把局部头一起抹了，
  于是"扫描器找不到成员"这个假结论被测成真的。修法是给 `ZipMap` 加
  `CentralDirectoryOffset / Length`，抹除必须用被测方自己报的边界。

还有一次是**断言里的直觉错误**：`压缩后大小必须小于原始大小` —— 随机数据上 Deflate 可以
比原文更大几个字节。这类断言写死了不是事实而是想象。

### 18. Avalonia headless 界面测试：四个坑，以及它当场逮到的一个崩溃

`tests/Andzip.App.UI.Tests`（`Avalonia.Headless.XUnit` + `UseSkia` + `UseHeadlessDrawing = false`）。
搭起来踩了四下：

- 窗口不 `Show()` 就没有视觉树，从它往下什么控件都找不到；`Show()` 之后还要 `Measure/Arrange`。
- `Control.LogicalChildren` 是 `protected`，得用 `GetLogicalChildren()` 扩展。
- Avalonia 里 `RadioButton` / `CheckBox` 都**派生自 `Button`**，`switch` 的 arm 顺序反了
  编译器直接报 CS8510（这个报错是好事，说明作者知道自己在写不可达分支的人不多）。
- `RaiseEvent(Button.ClickEvent)` **不会切换控件自己的状态** —— `Button.OnClick` 由指针管线调用。
  所以点 `RadioButton` 要直接设 `IsChecked`；第一版用事件点击，截出来的图还是"没选中第三种模式"，
  一张假截图比没有截图更误导。

值不值？第一次跑就抓到一个**用户一点就崩**的生产 bug：`RepairWindow` 里三个
`IsCheckedChanged` 处理程序的闭包捕获了 `for` 的循环变量，全都看到 `i == 3`，
`_modes[3]` 直接 `IndexOutOfRangeException`。纯逻辑测试看不见它 —— 它崩在事件处理程序里，
只有真的把窗口装配起来、真的去点，才会暴露。

真实窗口的核对另走一条路：`tests/capture-windows.ps1` 启动真 exe、前台化、按窗口矩形截屏
（`PrintWindow` 对 Avalonia 的 GPU 表面常拿到黑块）。这里也有个坑：**不加
`SetProcessDPIAware()`，截图像素与 `SetCursorPos` 坐标被 DPI 虚拟化**，按图算出来的点击
会落到别处 —— 第一次点「压缩」没反应就是这个原因。

### 19. 0.9.11 的闪退：`Progress<T>` 捕获的上下文不是 Avalonia 的，而 headless 不查线程亲和性

用户报"测试压缩文件时会闪退"。而 0.9.11 那 14 条界面测试**全绿**。

决定性证据是 Windows 应用程序日志里的 1026 栈：

```
System.InvalidOperationException: Call from invalid thread
   at Avalonia.Controls.ProgressBar.set_IsIndeterminate(Boolean)
   at Andzip.App.Views.ProgressWindow.Update(ArchiveProgress progress)
   at System.Progress`1.InvokeHandlers(Object state)
   at System.Threading.SynchronizationContext.<>c.<Post>b__8_0(KeyValuePair`2 s)
   at System.Threading.QueueUserWorkItemCallbackDefaultContext`1.Execute()
   at System.Threading.ThreadPoolWorkQueue.Dispatch()
```

倒数第三帧是关键：`Progress<T>` 捕获到的那个 `SynchronizationContext`，它的 `Post` 是
**基类的默认实现 —— 丢线程池**。也就是说捕获到的根本不是 Avalonia 的上下文。
于是池线程直接去改 `ProgressBar`，异常在 `ThreadPoolWorkQueue` 里抛出，没人接，进程带走。
结论一句话：**"回到 UI 线程"这件事不能寄托在环境上下文上**。
现在由 `ProgressWindow.CreateSink()` 显式走 `Dispatcher.UIThread.Post`，
所以在哪个线程构造、由哪个线程上报都无所谓 —— 六个调用点全部换成它。

第一条诊断是**错的**，而且错得很有代表性。当时的说法是：`new Progress<T>(window.Update)`
写在 `Task.Run` 的 lambda 里，捕获到的上下文是 null，所以只要把它提到 UI 线程构造就好了。
听起来通，动手也照做了 —— 但 `ExecutionContext` 是会流进 `Task.Run` 的，
提到外面构造和在里面构造捕获到的是同一个东西，什么都没改变。
推翻它的是我自己写的那条回归测试：它按"错误理论"应该失败，结果它通过了。
**教训：回归测试要复现的是生产环境的线程形状，不是我的猜想。**

第二条坑让上面这件事更晚被看清：`dotnet build src/Andzip.App` 写的是
`bin/Release/net10.0/`，而真机验证启动的是 `bin/Release/net10.0/win-x64/Andzip.exe` ——
那是上一次 `publish` 的产物。"我改好了，怎么还崩"里有一半是在测旧二进制。
现在验证前先跑 `build.ps1`，或者直接看文件时间戳。

第三条：带文件路径启动会遵守"双击直接解压"这个设置，程序直接去解压、窗口都不出现，
`Ctrl+T` 永远打不到。要加 `/task=open` 才会开列表窗。

为什么 14 条界面测试抓不到？**headless 平台不检查线程亲和性** —— 从池线程改控件在这里不抛。
所以新加的 `ProgressWindowThreadingTests` 断言的不是"有没有炸"，而是
"回调落在哪个线程"：上报之后先断言窗口**还没**动（说明只是被排进队列），
`Dispatcher.UIThread.RunJobs()` 之后才断言它动了。
另外还留了一条端到端：真包、真引擎、真进度窗口、后台线程跑完整性检测。

有一条反面对照（裸 `Progress<T>` 在无上下文时投递到工作线程）写完就删了：
那条投递是异步的，断言只能靠轮询等它跑完 —— 会随机变红的测试不如不写。
机制本身留在 `CreateSink` 的注释里，证据就是上面这段栈。

修复后的真机核对：`box.zip` → `Ctrl+T` → 「测试完成 / 所有成员校验通过，没有发现损坏」，
进程存活，事件日志 0 条新崩溃。

### 20. 右键菜单这件事可以用程序验证：`Verbs()` 就是资源管理器看到的那张菜单

0.10.0 这轮要改右键动词集合，其中"压缩包身上不要再出现压缩项"靠的是注册表里的
`AppliesTo` —— 一个我原本不确定存在的机制。没有验证手段的话，这种改动只能"写完发给用户，
等他告诉我有没有生效"。实际上有两条能当场问清楚的路：

- **`Shell.Application` 的 `FolderItem.Verbs()`** 返回的就是资源管理器给这个文件列出的菜单。
  脚本化之后能直接断言"box.zip 上没有「压缩为 ZIP」、note.txt 上还有"。
- **直接读回注册表**：`HKCU\Software\Classes\Andzip.zip\shell` 与 `…\*\shell`，
  看动词键、命令行、`AppliesTo`、`ProgrammaticAccessOnly` 到底写成了什么。

量出来的结论：

- `AppliesTo = "NOT (System.FileExtension:=.zip OR …)"` 确实能隐藏动词。
  49 个扩展名的长查询（1447 字符）照样生效，不是只有三五个词的时候能用。
  这是本机别的软件在用的写法（`removeproperties` 那条动词就带它），不是我编的。
- `ProgrammaticAccessOnly` 能让一个动词**从菜单上消失但仍然可被调用**。
  这一点是整轮改动的前提：右键的「用 Andzip 打开」和双击用的是同一条 `shell\open`，
  要把"打开"这个名字变成真的打开，就得让 `open` 藏起来专管双击，另外立一条
  `andzip-open` 给菜单。藏起来之后双击还灵不灵？实测：`double_click_action = extract`
  的用户双击仍然直接解压，右键「打开」仍然开主窗口 —— 两条互不干扰。
- **动词键写了不等于旧的消失了**。`RepairVerbs` / `WriteCommands` 都只增不改，
  所以撤掉「压缩为 7Z」必须显式 `DeleteSubKeyTree`，否则菜单上是新旧并存。
- **资源管理器的动词表有缓存**。写完注册表立刻 `Verbs()` 会读到半套（那次只看到
  「用 Andzip 打开」一条，其余全空），过一会儿再枚举才是对的。差点把缓存当成 bug 去改代码。

顺带一条与界面无关的事实：Avalonia 的按钮模板里放的是 `AccessText`（`TextBlock` 的子类），
所以按类型找 `TextBlock` 时会连按钮里那个一起找到 —— 测试里别用"树里只有一个 TextBlock"来定位。

### 21. 拖放为什么测不了：`IStorageItem` 不允许用户代码实现

0.11.0 加主窗口拖拽时，本来想在 headless 里把一次真实的 `DropEvent` 打进 `MainWindow`，
好证明"事件确实注册在窗口上、路由到了对的分支"。做法是造一个只回答文件那一种格式的假
`IDataTransfer`，塞一个假 `IStorageItem` 进去。

前半段是通的：`DataTransfer` / `DataTransferItem.CreateFile` / `DragEventArgs` 都能直接构造
（顺带踩掉三个 `CS0618`：`DragEventArgs.Data`、`IDataObject`、`DataFormats.FileNames` 在
11.3 里都已经过时，新 API 是 `e.DataTransfer` + `DataFormat.File` + `TryGetFiles()`；
门禁要求 0 警告，所以必须用新的）。

后半段撞墙：编译器明确报

```
CS0535: 不实现接口成员 IStorageItem.(This interface or abstract class is -not- implementable by user code !)()
```

Avalonia 在 `IStorageItem` 上放了一个私有接口成员，专门挡第三方实现。
所以假的数据对象造不出来，这条测试被删掉了 —— **拖进来的东西到底有没有反应，仍然只能人拖一次**。

这不是"测试没写"而是"这层测不到"，两者的区别要写清楚：判断逻辑本身（哪个路径该打开、
哪批该压成一个新包）已经挪进 `ShellTasks.RouteDroppedPaths` 并在 Core 里测了，
`ArchiveFormatOption.IsReadablePath` 也有单测（包括"名字叫 `photos.zip` 的文件夹不算包"）。
剩下没覆盖的是操作系统那一层的投递。

### 22. 核对一个对话框：枚举进程的所有顶层窗口，而不是 `MainWindowHandle`

0.11.1 要核对「选择解压路径」改版后的样子，顺带踩了两下，都值得记下来。

**`Get-Process` 的 `MainWindowHandle` 拿不到模态子对话框。** 主窗口开着的 `ShowDialog`
窗口属于同一个进程但不是"主窗口"，所以按 `MainWindowTitle` 找会一无所获 —— 那次它回过来
一个 1582×1215 的截屏，其实是主窗口。正确做法是 `EnumWindows` + `GetWindowThreadProcessId`
把该进程所有 `IsWindowVisible` 的顶层窗口列出来，逐个 `GetWindowRect` + `CopyFromScreen`。
系统的文件夹选择对话框也是**同进程**的（`IFileOpenDialog` 是 in-proc COM），
所以"弹没弹"只能靠"点之前/点之后窗口集合的差集"来判断，不能靠进程名。

**同一个坑第二次踩：`dotnet build src/Andzip.App` 不写 `win-x64` 那份。**
它输出到 `bin/Release/net10.0/Andzip.dll`，而我启动的是
`bin/Release/net10.0/win-x64/Andzip.exe` —— 那是上一次 `build.ps1` 留下的。
现象是"改了高度，截屏量出来还是老尺寸"，跟 0.9.12 那次"修好了还崩"一模一样。
要么 `dotnet build -r win-x64`，要么直接跑 `build.ps1`；核对之前先看一眼两个 dll 的时间戳。
（这次量到的窗口是 1072×494 物理像素，改的是 700×292 DIP，1.5 倍 DPI 加边框 ——
所以判断"跑的是不是新二进制"要看数字，不能凭感觉。）

**`SendKeys` 的助记符不可信**：按钮文案里的 `(&B)` 在 Avalonia 里是**字面文本**，
`Alt+B` 不会触发它（这正是 0.10.0 要把它去掉的原因）。要点按钮就得按坐标真点一下
（`SetCursorPos` + `mouse_event`），或者走 `SendKeys` 发那些**真的**注册了的快捷键（`Ctrl+E` 好用）。

**PowerShell 脚本里不要写中文字面量**：Windows PowerShell 5.1 按本地代码页读没有 BOM 的
UTF-8 文件，`-like '*解压路径*'` 里的中文进了脚本就成了乱码，匹配永远失败。
要判断窗口身份就用结构性的特征（尺寸、pid、窗口集合的差集），或者把脚本存成带 BOM 的 UTF-8。

**`Get-Process Andzip` 匹配不到版本化的产物名。** 进程名来自文件名，
`Andzip-v0.11.1-win-x64.exe` 的进程叫 `Andzip-v0.11.1-win-x64`。截图脚本收尾用
`Get-Process Andzip | Stop-Process` 清残留，一个也没杀掉，于是三个窗口留在桌面上，
而且**产物文件被自己的进程锁着**，`build.ps1` 重发同一版本时报的是"访问被拒绝"。
按 `Path -like '*Andzip*'` 匹配才对。同一件事也解释了为什么那次删除失败看起来像权限问题。

**`Move-Item -Force` 不覆盖已存在的文件**（只压 read-only 属性），所以重发同一个版本号
必然失败。修 `build.ps1` 之前撞过两回，都是靠改版本号绕过去的 —— 那是掩盖，不是修。

### 23. 头加密的 7z 在引擎那里"没有口令"这个事实：它报的是"这不是压缩包"

用户报「本次运行中记住用过的口令」没生效。顺着这条设置往下找，结论是**设置本身没问题**，
问题是它从来没有机会生效 —— 头加密的 7z 压根不弹口令框。

量出来的链条：

- `azcore list pw-enc.7z`（不给口令）→ `az_archive_open failed (7): not a recognised archive format`。
  7 是 `AZ_ERROR_BAD_FORMAT`，不是 8（`AZ_ERROR_PASSWORD`）。
- 原因在 7-Zip 自己：`7zIn.cpp` 第 405 行的注释写着 "S_FALSE means that file is not archive"，
  而 `az_reader.cpp` 的格式轮询把 `S_FALSE` 记成"这个处理器说不是它的活"，
  只有硬错误（`res != S_FALSE`）才会带出去。头加密时处理器返回的就是 `S_FALSE`。
- 于是 `NativeEngine.Translate` 把 `BAD_FORMAT` 变成 `ArchiveConstraintException(格式不支持)`，
  `MainWindow.OpenArchive` 弹出的是「该格式不支持」；
  `ArchiveExtractor.IsPasswordProtected` 只认 `ErrorPassword`，所以返回 `false`，
  解压/测试也都不问口令，直接失败。

**能用来分开的只剩文件自己的魔数**：签名是 7z、处理器却说"不是压缩包" ⇒ 缺口令。
中途试过两条更"精确"的路，都不成立：
一是照网上流传的说法读下一个头的属性字节 `0x23`（`kEncodedHeader`）—— 实测 7-Zip 26 的
起始头里 `Reserved[4]` 非零、`NextHeaderOffset` 指向 224 而不是 32，属性枚举里
`kEncodedHeader` 数下来是 **23 十进制 = 0x17** 而不是 0x23，凭记忆写死就是错的；
二是找 7-Zip 的"已加密"标志 —— 打不开就没有任何归档属性可读。
所以留下的是签名这一条，代价写在代码注释里：**真坏掉的 7z 会多弹一次口令框**，
输完仍然报原来的错。只管 7z：ZIP 中央目录是明文（走 `IsEncrypted` 正路），
RAR 没有可写入的样本，没量过就不下结论。

**两条工具链上的教训**：

- **headless 测试平台上 `Application.Current.ApplicationLifetime` 是 `null`**。
  所以"枚举应用窗口、看这次弹的是口令框还是错误框"这类断言在 headless 里做不到 ——
  我按这个思路写的两条界面测试注定超时失败，删掉了。要观察弹了哪个对话框，
  就去真机枚举进程窗口（`EnumWindows` + `GetWindowThreadProcessId`）。
  改判本身由 Core 的 5 条单测钉住，那才是该被自动化的那一层。
- **P/Invoke 取窗口标题必须写 `CharSet = CharSet.Unicode`**。不写的话 `StringBuilder`
  按 ANSI 封送，中文标题回来是 `曪?` / `搹eQ芠x` 这种乱码 —— 而且它看起来"像个结果"，
  容易当成编码问题绕过去。

真机前后对比（同一个 `pw-enc.7z`，枚举进程可见窗口标题）：
0.11.1 的产物是「错误」，改判之后是「输入密码」。

### 24. 验证"真的进了回收站"，以及界面测试里"在 UI 线程上等 UI 线程"

1.3.0 加「删除压缩文件」时踩到三条，都不是编译能告诉你的：

- **`task.Wait()` 在 UI 线程上就是自己等自己**。`AvaloniaFact` 的测试体跑在 Dispatcher 线程上，
  而 `MainWindow.OpenArchive` 里是 `await Task.Run(...)` —— 续体要回到同一个 Dispatcher 线程才能跑。
  写 `window.OpenArchive(archive).Wait(TimeSpan.FromSeconds(10))` 之后：线程被 `Wait` 占死，
  续体永远进不来，10 秒后超时，而失败信息长得像"这功能压根没生效"。
  更难看的是整批一起跑时测试宿主直接以 `0xC0000409` 退出 —— 被抛弃的续体在 harness 拆台之后才落地。
  现在有了 `UiWait.Until`：等的时候反复 `Dispatcher.UIThread.RunJobs()`，续体有机会跑完。
  规矩一句话：**在 UI 线程上不要阻塞等待一个会回到 UI 线程的 Task**。
- **"文件不见了"不是"进了回收站"的证据**，`File.Delete` 也能让它不见。要断言就得去
  `C:\$Recycle.Bin` 核对，而那里第一条假设就错了：**数据文件不叫 `$R<原名>`**。
  Windows 把它改名成 `$R` + 一个七位随机短名（原名太长 / 带连字符这类不该出现在 8.3 里的字符时留不住），
  真正的原名与完整路径记在**配对的 `$I` 元数据**里（UTF-16）。所以按 `$R andzip-recycle-probe.txt`
  去找会一无所获，得遍历 `$I*`、把内容按 UTF-16 摊开、找那条原始路径。本机实测：
  `$I8R75IN.txt` → `C:\Users\frank\AppData\Local\Temp\andzip-recycle-…\andzip-recycle-probe.txt`。
  顺带两条查过的事实：`SHFileOperationW` 返回 0 **也不能**证明它被回收（直接删也返回 0）；
  这台机器 `HKCU\...\Policies\Explorer` 没有 `NoRecycleFiles`、`Explorer\BitBucket` 下没有按盘的键，
  也就是回收站是开着的 —— 排查时先排除这种环境性原因，不然会去改本来正确的代码。
  清理也要成对：只删 `$R` 会在用户的回收站里留下一条点不开的记录。
- **注释里写了"要能拿到 internal"，不等于真的能拿到**。`Andzip.App.UI.Tests.csproj` 从一开始就有
  这句注释，但仓库里从来没有 `InternalsVisibleTo`，于是 `MnemonicText.Label`、`RecycleBin`、
  `ArchiveReveal` 全在射程外。后果不是"测试跑不起来"，而是**测试绕开了它本来该问的问题** ——
  比的是语言包原文而不是界面上渲染出来的文字，`(&X)` 那类缺陷就从这一层漏过去了。
  现在补上这条声明，并把那条比较改成走 `Label`。

### 25. 规则只活在文档和记忆里，就等于没有规则：`0.13.0` 应为 `1.3.0`

版本号规则是用户 2026-10-12 定的：`A.B.C` 三段、**每一位一个十进制位（0-9）**、满了向左边进一。
2026-10-13 我发出了 `0.13.0` —— 第二位写成了两位数字，而按规则它应该是 `1.3.0`。

为什么会犯：那几版是按"小功能 → 第二位 +1"机械推的，`0.12.0 + 1 = 0.13.0` 看起来完全合规，
而"每一位只有 0-9"这一半没被想起来。真正的问题是**没有任何一道关卡会为此报错**：

- `VersionInfo.Parse` 只要求 `System.Version` 解析得动，`0.13.0` 当然解析得动；
  它的异常文案甚至写着"语义化版本" —— 那份文档自己就在教人犯这个错。
- `build.ps1` 的正则是 `[0-9]+\.[0-9]+\.[0-9]+`，`+` 而不是单个字符。
- 测试里没有一条断言涉及"段宽"。
- 反例其实就摆在 `CHANGELOG.md` 里：`0.9.10 / 0.9.11 / 0.9.12` 是规则说清楚之前的编号，
  当时为了不做历史重编号专门写了"不回改"—— 那等于把两位数的写法留在了文件里当先例。

修法是把规则挪到会被执行的地方：`VersionInfo.Parse` 现在要求三段、每段一位数字，
拒绝时的消息顺带教怎么进位（光拒绝不够，被拒的人只会再猜一种写法）；`build.ps1` 的正则
收紧成 `[0-9]\.[0-9]\.[0-9]`；测试补 11 条，其中 `0.13.0` 与 `0.9.10` 是真实犯过的两个形状。
本次的 `0.13.0` 直接改叫 `1.3.0`（产物、CHANGELOG、文档、`VersionNo.ini` 一起改），
已经推上去的那几个 `0.10.x`–`0.12.0` 提交与 exe 不回改。

一句话的教训：**凡是希望别人（包括下一次的我）遵守的规则，要么写进类型，要么写进断言，
否则它只在"恰好想起来"的那一次生效。**

### 26. 「设置不生效」的真正原因不在那个设置上：两份 `AppSettings` 实例，写盘是整份盖

用户报的是「自动展开树里的文件夹」这条勾了没反应。查下去发现两件事，都跟这条开关无关：

- **主窗口与设置窗口各持一份 `AppSettings`。** 设置页点「立即应用」时走的是
  `AppSettings.Load(path)` → 改 → `Save(path)`，写的是**磁盘**；主窗口手里那份还是启动时读的。
  对话框关掉后 `ApplyViewDefaults()` 从**自己那份**读 → 读到旧值 → 界面不动。
  这一条影响查看页全部五项，不止自动展开。
- **更糟的是覆盖写。** 主窗口之后任何一次写盘（记最近的文件、记住上次输出目录）都是
  `Save` 整份快照 → 把设置窗口刚写的那一行抹掉。于是"设置不生效"升级成"设置连重启都找不回来"。
  现场证据：用户机器上的 `settings.ini` 只剩两行注释、**一个键都没有** ——
  他确实应用过，那份文件后来被旧快照盖回去了。

修法：`AppSettings.Reload(path)` **就地**替换字典内容（换新实例没用，引用已经发出去了），
主窗口在设置对话框关掉之后、重新应用之前先 `Reload`。

教训有两层：

1. 一个"整份快照写盘"的存储，只要存在第二个写者，就必须有重读这一步 —— 要么写前重读，
   要么改成按键写。这里选了前者，因为写者只有主窗口与它自己弹出的模态对话框，顺序是确定的。
2. 用户说"这条设置不生效"时，**先假设他说的是症状而不是原因**。开关本身的代码
   （`ArchiveView.CreateTreeItem` 里那句 `item.IsExpanded = _view.AutoExpandTree`）是对的 ——
   我先写的两条 headless 用例直接构造 `ArchiveView` 传 `ViewDefaults`，两条都绿，
   这恰好证明"视图层没问题、问题在值怎么到视图层"。要是从开关本身读起，会一直找不到。

顺带按用户要求把默认值改成**不展开**（`ViewDefaults.Fallback` 与 `Load` 的 fallback 一起改）。
这是这一页上唯一偏离"引入设置页之前的界面"的缺省值，理由写在 `ViewDefaults` 的注释里：
深包一打开就摊平，第一屏全是文件夹名，看不到内容。

### 27. `DockPanel.SetDock` 设在孙元素上没用：菜单栏变成左边一整列之后

改版时给菜单栏包了一层 `Border`（为了那条 1px 下边线）。原来的代码是
`DockPanel.SetDock(menuBar, Dock.Top)`，包一层之后这行没动 —— 于是 **Dock 附在菜单自己身上，
而 DockPanel 只看它直接子元素的值**。结果菜单栏变成占满左侧的一整列，
工具栏被挤到右边半屏，蓝带只覆盖右半边。截图一眼就看出来了，但代码上没有任何报错或警告。

教训：**给一个已经挂在容器上的控件再加一层包装时，挂在原控件上的容器附加属性必须一起搬过去。**
`DockPanel`/`Grid.SetRow`/`Grid.SetColumn` 这类"由父容器读取的附加属性"，
一旦层级变了就会静默失效。这类问题编译期、单测都看不见，只有把窗口真的画出来才看得见 ——
这也是为什么 `tests/capture-windows.ps1` 和 headless 渲染截图一直留在这套门禁里。

### 28. 「返回 S_OK」不等于「屏幕上变了」：DWM 深色标题栏在这台机器上不生效

夜间模式想让标题栏一起变深，用的是 Windows 的
`DwmSetWindowAttribute(hwnd, DWMWA_USE_IMMERSIVE_DARK_MODE = 20, &1, 4)`（18985 之前是 19，
所以两个都试）。代码是对的、调用是成功的：

| 试过的动作 | 结果 |
|---|---|
| `DwmSetWindowAttribute(..., 20, 1, 4)` | 返回 `0`（`S_OK`） |
| 同一个句子上试 `19` | 返回 `-2147024809`（参数错误，符合预期：这个版本只认 20） |
| 补一次 `SetWindowPos(SWP_FRAMECHANGED)` | 返回 `True` |
| 补一次最小化 + 恢复 | — |
| **标题栏中点像素** | 前后都是 `rgb(248,248,247)`，**一点没变** |

也就是说 API 接受了这个属性，DWM 没有照它重画非客户区。这台机器是 Windows 10 19045，
系统"默认应用模式"是浅色 —— 有资料说这条属性在 Win11 上才稳定生效，但本机没法验证。

三条可复用的结论：

1. **P/Invoke 返回成功只证明"系统收下了参数"**，不证明用户看得见效果。
   凡是"调用成功 = 功能生效"的推断，都要再用屏幕上的事实核一次（截图取像素，或者人眼看）。
   这次如果只看返回值，README 里就会写上一句"标题栏会跟着变深"—— 那是假话。
2. 所以文档与代码里都改成**如实描述**：属性照设（Win11 上大概率有效、且失败无害），
   但规范 §10.3 与 README 的已知限制里写明"本机实测不生效、不作为交付效果"。
3. 判定"某个视觉属性有没有生效"的最小手段就是取一个点的颜色：
   `Pixels.At(window, point)`（`UiHarness.cs`），比读控件属性硬一个层级。

### 29. 同一个成因换了位置：第 26 条的整份覆盖，这次发生在设置窗口的两页之间

第 26 条讲的是"主窗口拿旧快照写盘，把设置盖掉"。1.6.0 把「双击压缩包时」从常规页搬到解压页时，
同一个形状在**设置窗口内部**又出现了一次，只是主角换成了两个页面：

| 页面 | 落盘时机 | 用的是哪份 `AppSettings` |
|---|---|---|
| 解压 / 查看 / 压缩 / 安全 / 高级 / 语言 | 点「立即应用」 | 自己 `Load` 的一份（新鲜） |
| 常规 / 文件关联 / 上下文菜单 | 「确定」或点应用 | **主窗口传进来的那一份**（窗口打开时的快照） |

于是：在解压页把双击改成「直接解压」并应用 → 磁盘上已经是 `extract`；切到常规页勾掉 Esc、
点「确定」→ 常规页把**窗口打开那一刻的整份快照**写回去，`double_click_action` 又变回 `open`。
用户看到的就是"两个设置只能记住一个"。

修法是一个入口：`SettingsWindow.Persist(shared, path, mutate)` —— **从磁盘重读、只改自己那几项、
写回、再把主窗口那份快照 `Reload` 上新值**。最后一步同样必要，否则主窗口下次写盘（记最近的文件）
又是一次旧盖新。

这条的价值不在修法（跟第 26 条一模一样），在**验证方式**：新写的
`GeneralPageOkDoesNotEraseWhatTheExtractPageApplied` 先按旧写法跑了一遍，**红了**；
换回 `Persist` 才绿。一个"看起来显然会失败"的断言，如果不真正确认它能失败，
就只是一句写在测试里的愿望 —— 第 26 条那次也是先有了断言才发现自己测的是错的方向。

可复用的结论：**只要一个文件被多处写，"谁持有最新快照"就必须有唯一答案**。
要么所有写入者都从磁盘重读（本项目现在的做法），要么只有一个写入者。混着用就是这次这个 bug。

### 30. 程序图标：AI 出图更好看但不能用，于是 16px 变成另一张图

用户要"高大上一点的 AppIcon"。先用出图工具生成了两张 1024 候选 —— 确实比手画的精致
（渐变、软影、金属拉头），但**右下角带一枚去不掉的"AI 生成"水印**，而这是要编进 exe
的资源、还要出现在右键菜单和「打开方式」里。所以换成代码画：`assets/make_icon.py`，
Pillow + 8 倍超采样，规范 §6.4 记几何意图，脚本是它的机器版本。

换做法之后才发现真正的问题不是"好不好看"，而是**旧图标根本没有 16px 那一份**：
`andzip.ico` 里只有一条 256px 的 PNG 条目（2538 字节），标题栏和任务栏上那点大
是 shell 自己缩出来的。于是三件事变成必须自己决定：

1. **小尺寸是另一张图**。16px 上拉链齿会糊成一团、软投影会变成一圈脏边、拉头上的凹槽
   会把它啃成暗点。所以 `tier="small"` 直接去掉这三样，只留"两块白纸 + 一个放大的琥珀拉头"，
   中缝让方块的蓝透出来。16/24/32 用这一版，48 以上用完整版。
2. **ICO 容器混用两种编码**。16/24/32 存 32 位无压缩 DIB，48+ 存 PNG。PNG 条目的 16px
   在 Office / Outlook 那类老组件里会读成一片空白，而 Windows shell 自己完全正常 ——
   这类"我这里好好的"最难查，所以宁可让文件大 3KB。
3. **颜色要跟界面同源**。方块的中间色就是 `Design.BrandBase`（`#0F6CBD`），拉头是
   `FolderFace`/`FolderEdge` 那一族琥珀 —— 与内容区出现频率最高的文件夹图标同色。
   这样"图标是另一个蓝"这种漂移不可能发生，因为只有一个来源。

验证方式：`AssetIconTests` 解析 ICO 目录（七档齐全、大小顺序、编码类型、`<ApplicationIcon>`
指的就是这份文件），加真机截图。截图里能看到的顺序是标题栏 16px、任务栏 24/32px、
设置窗口标题栏 16px —— 三处都认得出"蓝底 + 两张白纸 + 琥珀拉头"。

顺带一条通用结论：**AI 出图的水印要在一开始就问"这东西最终进不进产品"**。
这次如果先精修完再发现水印，前面所有调色都白做。

### 31. 无边框圆角窗口：先量"这台机器让不让"，再谈设计

用户要"主框体本身圆角加阴影"。这件事有一半是平台问题，不是 CSS 问题，所以顺序是**先探后写**
（这一条规矩在 1.4.0 的圆角上救过一次、在 1.5.0 的 DWM 上救过一次）。

三条探针，全部量像素：

| 要问的问题 | 怎么问 | 结果 |
|---|---|---|
| `Border.BoxShadow` 到底画不画得出来？ | 白面板坐在浅灰底上，取面板右缘**外** 4px 那个点，问它比底色暗没暗 | 暗 —— 画得出来。规范 §二 原来那句"SimpleTheme 用不了阴影"说的是**模板控件**（Button 根本没有 `BoxShadow` 这个属性），不是 Border |
| 透明窗口在这台 Win10 19045 上生不生效？ | 临时把主窗口设成 `Transparent` + 扩展客户端区 + 无系统按钮，`dotnet run` 之后全屏截图，看圆角外那圈透出的是桌面还是白 | 透出后面的窗口，阴影也在 —— 成立。**这一步不能省**：1.5.0 那条 DWM 深色标题栏就是"返回 `S_OK`、屏幕上一点没变" |
| `ToggleButton` 的轨道色归谁？ | 把轨道设成控件自己的 `Background`，截设置页 | 变成模板灰。模板对 `:checked` 有它自己的 setter，我们赋的蓝被盖掉 —— 于是"开着 / 关着"只剩滑块位置之差 |

第三条最阴：属性值是对的（`toggle.Background` 读回来就是那支蓝刷），屏幕上不是。
凡是"设了颜色"的断言都会绿着放过去，只有量像素会红。
所以开关的视觉全部画在 Content 里那颗自绘 `Border` 上，控件本体只负责行为，
并且留一条断言：开着的轨道**必须**是品牌蓝。

选 `ExtendClientAreaToDecorationsHint` 而不是 `SystemDecorations=None`：前者只是把客户端区
铺满整窗、系统按钮关掉，贴边缩放、Win+方向键分屏、任务栏让位这些系统行为都还在；
后者要自己实现调整大小的命中区。真机核过最大化：正好铺满工作区、任务栏没被盖、
圆角与那圈透明边距自动收掉（`FitSurfaceToState`）。

**顺带白捡的一件事**：1.5.0 那条"深色标题栏翻不深"的已知缺陷直接消失了 ——
标题栏现在是我们画的，跟着调色板走，不再求 DWM。

### 32. 颜色抄死在 `static readonly` 里：切主题时它不动，而且没人报错

改版过程中截图发现设置页的分组标题在深色下是一片发灰的浅色字。原因是这一行：

```csharp
private static readonly IBrush PageText = Design.Ink.Primary;   // 错
private static IBrush PageText => Design.Ink.Primary;           // 对
```

字段在**类型第一次被碰到**时求值一次，把当时那套调色板的画刷抄死了；`Design.Use(dark: true)`
之后它还是旧的那支。本工程没有 XAML、颜色全从 `Design` 取，所以这个坑对**每一个**抄过色的人
都成立 —— 而 `Design` 自己把颜色做成属性（而不是字段）正是为了躲这件事，视图里却漏了。

处理方式与版本号规则同一个套路：**规则落到断言上**。
`DesignTokenTests.BrushesMustNotBeFrozenIntoStaticFields` 扫 `src/Andzip.App/**/*.cs`，
出现 `static readonly IBrush` 就红。同一条测试文件里已经有"禁止裸色值"的扫描，两条形同一族：
写在文档里的规则只会在"恰好想起来"的那次生效。

同一个提交里还修了一处同类问题：换主题时 `ApplyTheme` 只重刷了卡片底色，
**工具栏整条没重做** —— 它的图标与文字色是构造时取的一次，于是深色下"打开 / 解压 / 新建"
三个词变成深灰压深灰、看着像少了三个按钮，而禁用项（本来就用较淡的灰）反而还在。
现在 `ApplyTheme` 重建整条工具栏，`CardLanguageTests` 里那条"标题栏文字必须跟着调色板"盯着它。

### 建议你手动过一遍的清单

1. 新建 → 选一个含中文文件名的文件夹 → 格式 **7Z** + 中文密码 → 开始 → 观察进度条百分比。
2. 打开第 1 步的包 → 确认列表正常 → 解压到已有文件的目录 → 触发「重名询问」→ 选自动重命名。
3. 新建 → 格式 **ZIP** + 中文密码 → 应看到明确的「ZIP 密码仅支持 ASCII」提示，而不是英文报错。
4. 新建 → ZIP + 分卷 3MB → 压一个 10 MB 的文件 → 确认 `name.z01`、`name.zip` 生成，
   且能整体解压回去。
5. 打开 `.tar.gz` / `.tgz` → 确认列表显示的是内层 tar 的内容而不是一个成员文件。
6. F5 → 文件关联页：勾选状态应当与系统实际一致（第一次打开基本全是空的，除非以前关联过）。
   勾 ZIP → 立即应用 → **双击一个 .zip 应当直接用 Andzip 打开**，右键「打开方式」里也应当有 Andzip。
7. 再取消 ZIP → 立即应用 → 双击应当回到原来的默认程序（不是 Andzip，也不是没反应）。
   若某扩展名被 Windows 默认应用保护挡住，会**直接打开系统设置里对应的默认应用页**，不再只弹提示。
8. 应用后关掉设置再重开 F5：勾着的项目应当仍然勾着（说明注册表里真在）；点「重置」应当把未应用的
   改动读回系统状态，而不是恢复成一片预勾选。
9. F5 → 常规页 → 「双击压缩包文件时」选 **直接解压** → 确定 → 在资源管理器里双击一个 .zip：
   应当**只弹进度条**、解到同名的 `<包名>\` 文件夹里、跑完进度条自己消失，任务管理器里不留进程。
   （升级后第一次双击可能仍走旧 exe；那一次之后注册表会被自动校正到新版本，再双击就对了。）
10. 常规页取消「解压过程中允许按 Esc 取消」→ 确定 → 解压一个大包时按 Esc 应当没反应，
    点「取消」按钮仍然有效。
11. **右键解压菜单在不在**：F5 → 上下文菜单 → 确认「为已关联的压缩包添加「解压」菜单项」是勾着的 →
    确定 → 在资源管理器里右键一个已关联的 .zip（Win11 上要先点「显示更多选项」）：
    应当**正好**看到「用 Andzip 打开 / 解压 / 解压并删除」三项，后两项**只弹百分比进度条，跑完自己消失**。
    老机器上如果还看得到「智能解压」「解压到当前文件夹」或 v0.9.5 的「直接解压到 "包名" 文件夹」，
    说明自愈还没跑过 —— 随便用关联打开一次包，它就会换成新的三条。
12. **解压 · 情形一（包里只有一个文件）**：拿一个 `.gz`（或只装了一个文件的 zip）右键「解压」
    → 那个文件**直接出现在压缩包所在目录**，不产生任何新文件夹。
13. **解压 · 情形二（整棵树一层包裹）**：右键 `docs.zip`（里面只有 `docs/…`）→ 当前目录直接出现

    而它的白字要读得清；列表选中行是深蓝底 + 浅字（**不是白字底**）；
    正文不该是纯白、底不该是纯黑（刺眼说明做坏了）。
    ③ 再选「跟随系统」→ 应用 → 应当立刻回到系统那套深浅；关掉程序重开，选择应当还在

    ④ **已知不完美，请顺便确认这些是真不完美而不是我漏了**：标题栏仍是浅色

    清单在规范 §10.4）。
    ⑤ 如果这几块里有哪块你天天要受，就说一声 —— 那才值得为它写 `ControlTheme`。

    ③ 重开设置窗口，选择应当还在。
    ④ **专门试一次跨页**：解压页改成「直接解压」并应用 → 切到常规页勾掉 Esc → 点「确定」→
    再切回解压页。双击那一项**应当还是「直接解压」**。这一条以前会翻车（第七节第 29 条），
    现在有断言拦着，但屏幕上再走一遍才算数。

## 十、维护约定

- **每次改动都要同步更新文档**：入口的 `README.md`（功能清单、构建步骤、许可证）与本文件
  （状态表、架构决策、已知限制、验证记录），改代码的同一个提交里改掉对应描述。
  过期的「未验证」「未实现」比没有文档更有害。
- **文档分工**：使用者与贡献者第一眼看到的必须是 `README.md`；本文件只放推导过程、
  踩坑定位与逐版本验证记录。往 `README.md` 里塞长篇诊断是错误做法（2026-10-12 就是这么
  长到近千行的，随后拆分）。
- 本文档与 `native/README.md` 用中文书写。注释分区：**`native/` 下的 C/C++ 用英文并且
  整个目录保持纯 ASCII**（内核工程没有加 `/utf-8`，源码里出现中文会触发 `C4819`，而编译器
  按本地代码页 936 读 UTF-8 字节是实打实的风险）；`src/` 下的 C# 沿用原工程风格（中文注释）。
- **版本号是 `A.B.C` 三段、每一位一个十进制位（0-9），满了向左边进一**（用户 2026-10-12 定的规则，
  不是语义化版本）。修 bug 动 C；小功能动 B、C 清零；大版本动 A、B 与 C 清零。
  所以 `0.9.9` 之后是 `1.0.0` —— 写成 `0.10.0` 就是把"第二位加一"误写成了两位数字。
  `BuildNo` 是独立的递增计数，不参与进位。
  这条以前只写在文档与记忆里，于是 2026-10-13 真出过一次 `0.13.0`（应为 `1.3.0`）；
  现在 `VersionInfo.Parse` 与 `build.ps1` 都会拒两位以上的段，规则改由代码把关（第七节第 25 条）。
  已发布的 `0.9.10`–`0.9.12` 与 `0.10.0`–`0.12.0` 属于规则说清楚之前的产物，**不回改历史**。
- 改完跑一条命令就够：**`powershell -ExecutionPolicy Bypass -File ci.ps1 -Static`**。它就是
  CI 的 Windows 作业跑的那一条，包含引擎构建、532 原生断言、导出表核对、静态库、解决方案
  构建、两套托管测试与打包。想跳过慢的部分：`-SkipEngine`（引擎没动时）、`-NoPackage`（不出
  绿色版时）。
- **门禁脚本必须能真的失败。** 只查 `$LASTEXITCODE` 是不够的：可执行文件找不到时抛的是
  终止错误而退出码不变，脚本会假绿（第七节第 14 条就是这么骗过一次）。新增步骤一律走
  `Invoke-Gate` / `Invoke-NativeStep`，它们同时捕获终止错误与非零退出并带标签抛出。
- CI 里 Linux 的托管测试是 `continue-on-error`，那是**故意**的：它从没在非 Windows 上跑过。
  要升格成硬门禁，先去看它报了什么，而不是直接把开关去掉。
- 改了 `native/` 的接口或构建，请同时更新 `native/README.md`（内核层的细节在那边）。
- 动过内核里跟 COM/`PROPVARIANT` 打交道代码后，除了测试套件，建议在 CLR 宿主里跑一轮上千次
  的写入循环 —— 这类未初始化内存的问题只在宿主内存被复用过的形状下才暴露（第七节第 10 条）。

## 十一、许可证与出处

`native/` 合并了多个上游，`native/third_party/MANIFEST.json` 是机器可读的来源记录。

| 组件 | 来源 | 许可证 |
|---|---|---|
| 7-Zip 引擎（`C/`、`CPP/`） | `cankao/7zip-main.zip` | LGPL-2.1-or-later **附 unRAR 限制** |
| zstd / lz4 / brotli / lizard 等 | `cankao/7-Zip-zstd-master.zip`、`cankao/NanaZip-main.zip` | BSD-3-Clause / MIT / BSD-2-Clause 等 |
| 上述组件的 7-Zip 封装 | `cankao/NanaZip-main.zip` | MIT |
| Zig（仅用于交叉编译，不进产物） | ziglang.org | MIT |
| SharpZipLib（**仅测试工程引用**，生产代码不依赖） | NuGet 1.4.2 | MIT |

发布前必须复核两件事：

1. **unRAR 限制**：可以解码 RAR，但不得据此支持 RAR 创建。要宣传什么 RAR 能力，先对照条款。
2. **LGPL 路线**：`andzip_core` 以 DLL 形式动态链接，走的是动态链接这条路；若改成静态链接
   发布，需要按 LGPL 提供相应便利。

`src/`、`tests/`、`native/src`、`native/include`、`native/tools`、`native/tests` 下的内容
都是本项目的原创工作，沿用 Andzip 自身的许可证。

> 注意：`cankao/`（上游原始压缩包）和 `Bandizip-RE/`、`Bandizip/`（逆向参考语料）都在
> 本目录**之外**。重新 vendor 需要 `cankao/`；日常构建不需要。`vendor-sources.ps1` 会在
> `Andzip/cankao` 与上一级 `cankao/` 两处探测，都找不到就报错并提示用
> `-SourceArchives <目录>` 指定；若你要把整个仓库收敛到 `Andzip/`，请先把 `cankao/`
> 留在能取到的地方，或删除前确认永远不再重新 vendor。
